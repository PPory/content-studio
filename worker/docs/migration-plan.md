# 迁移方案：Notion → D1 + 飞书 + Obsidian vault

> 状态：待确认 · 起草于 2026-08-14 · 存档回退点 `8e73a04`

## 为什么迁

不是因为 Notion 不好用，是因为**这个项目要开源分发给国内创作者**。别人跑起来要过的坎里，Telegram（必须梯子）和 Notion（梯子 + 5 步配置）是仅有的两道墙。Cloudflare、LLM key（DeepSeek 等国产兼容服务）、Node 这几项对"会 clone GitHub 项目的人"都不构成门槛。

顺带解决的：Notion 的 API 限流、没有批量写入、正文是独立资源这三条，一直在挤压 Cloudflare 免费版 50 subrequest 的预算。

## 目标与非目标

**目标**

- 换掉两道墙：Telegram → 飞书机器人，Notion → D1
- 长文归 vault：稿件以 Markdown 落进 Obsidian 知识库，能被反链和全文搜
- 保持一个 Worker，不拆第二个服务
- 别人 clone 之后，配置步骤压到最少

**非目标**

- 不做托管版、不代别人付 LLM 费用
- 不做双写（D1 同时写 Notion / 飞书多维表格）——一致性代价远超一个只读界面的价值
- 不引入 Supabase。pgvector 是唯一值得的理由，等标签检索明显不够用了再说
- 不在这轮改工作台。Worker 先稳定，工作台随后跟进

## 项目形态：合并成一个仓库

**结论：合并，但用一个仓库两个包，各自保留独立的构建和部署。**

合并的真正理由不是"两个项目太乱"，是**分发**——让别人 clone 两个仓库、分别配 `.env`、再手动把工作台指向自己的 Worker 地址，是纯摩擦。

```
content-studio/
├── CLAUDE.md          顶层：项目是什么、两个包的分工、红线
├── worker/            Cloudflare Worker（现 content-pipeline）
│   ├── CLAUDE.md
│   ├── wrangler.jsonc
│   ├── schema.sql
│   ├── src/
│   └── prompt/
└── workbench/         本地工作台（现 creator-workbench）
    ├── CLAUDE.md
    └── src/
```

**没有 `shared/` 包。** 这是刻意的——monorepo 里的共享包是最容易腐烂的地方。取而代之的是一条必须守住的原则：

> **Worker 是所有数据规则的唯一真源。工作台不定义任何数据规则。**

这条现在就成立（`/wb/*` 返回压平后的字段，不返回 Notion 原始 page 对象），换 D1 之后要继续守。新增的 vault 路径约定也走这条：**Worker 在响应里返回 `vaultPath`，工作台照着读，绝不自己拼路径**。两边各存一份路径规则，漂移是迟早的，而且是静默的。

**合并动作和开源动作一起做**：新建仓库、两个项目作为初始提交。理由是现有 git 历史里有隐私信息（Telegram `chat_id`、四个 Notion 库 ID、自建 LLM 域名 `your-llm-proxy.example.com`），清理当前文件不够，历史里还在。旧的两个仓库留在本地作存档。

## 本质变化：这是一次净删减，不是移植

从第一性原理看，多数改动不是"把 Notion 调用换成 SQL"，而是**拿掉一整层被 Notion 的数据模型逼出来的适配代码**。

| 机制 | 现在（被 Notion 逼出来的） | 之后（本来就该是的） |
|---|---|---|
| 幂等 | 任务标识写进页面正文，靠 `getPageText` 读回来查字符串 | 任务标识是表上的 `UNIQUE` 列，`INSERT ... ON CONFLICT DO NOTHING`。**正文里那行「系统任务标识：xxx」彻底消失**，不再污染内容 |
| 字段读写 | `plainTitle` / `selectName` / `toRelation` / `toStatus` 等约 20 个函数，在 property 结构里挖值包值 | **全部删除**。SQL 返回的行就是普通对象 |
| 关联 | 双向 relation，必须在 Notion UI 里设 No limit，写一边等另一边同步 | 关联表 `topic_materials(topic_id, material_id)`。天然多对多，没有 limit 这个概念 |
| 状态 | 字符串散在各文件，改 Notion 选项名代码就 400（「搬置→搁置」那次） | 常量集中一处 + `CHECK` 约束，改名走迁移脚本，不会静默出错 |
| 正文 | `mdToBlocks` / `getPageMarkdown` / `appendBlocks` / `clearBlocks`，一套转换 + 分块 + 分页 | `TEXT` 列直接存 Markdown。**`md2blocks.js` 整个删除**，`@tryfabric/martian` 依赖移除 |
| 补充素材检索 | 查 100 条候选拉回 Worker，本地按 `标签重合×2 + 关键词命中` 打分 | 一条 SQL。可以顺带加 FTS5 全文匹配、时间衰减、核验状态加权 |
| 批量写入 | 6 张素材卡 = 6 次 `createPage` | 1 条 `INSERT`。triage 一轮的调用数从 ~30 降到 ~12，批量参数可以放宽 |

**新增的复杂度只有三处**：写 GitHub（vault 归档）、飞书事件解密与幂等、`tenant_access_token` 缓存刷新。

净效果预计是代码减少，`lib/notion.js`（369 行）换成更小的 `lib/db.js`，`md2blocks.js`（31 行）归零。

## 目标架构

```
飞书机器人 ──事件(秒级)──┐
                        ↓
              Cloudflare Worker（唯一服务）
                   ├── D1：灵感 / 素材 / 选题 + 关联表
                   ├── LLM（DeepSeek 或其他 OpenAI 兼容）
                   └── GitHub API ──→ Obsidian vault（.md）
                        ↑
              creator-workbench（本地，读 /wb/* + 读 vault）
```

各自的角色，不重叠：

- **D1** = 状态机。机器高频读写的都在这
- **vault** = 长文与长期资产。人要读、要搜、要反链的都在这
- **飞书** = 移动端入口。随手扔灵感、卡片按钮拍板、`/状态` `/搜`
- **工作台** = 桌面全功能界面

一条判断依据，后面遇到"这个放哪"时直接套用：

> **机器要频繁读的，必须在 D1；人要读、要搜、要反链的，写一份到 vault。**

反例说明为什么：成稿时 `fetchSupplementary` 要扫 100 条候选素材的正文打分——在 D1 是 1 次 SQL，在 vault 是 100 次 GitHub API，直接爆掉 50 的上限。读路径一旦走 GitHub 就完了。

### 谁住在哪

| | 真源 | 何时写 vault |
|---|---|---|
| 灵感 | D1 | 初筛完成时写原文；**仅「已弃用」不写**（明确判过没价值的，写进去是噪音） |
| 素材 | D1 | 创建即写——长期资产，要在 Obsidian 里搜和反链 |
| 选题 | D1 | 成稿时，连同稿件一起 |
| 稿件 | **vault** | 成稿即写，D1 只留一行索引（含 `vault_path`） |

稿件是唯一 vault 为真源的：成稿之后全是人在读在改，机器不再回头读它。

灵感原文保留是刻意的——素材卡是 LLM 提炼的，一定会丢信息。写作时回看「当时到底看到了什么」，这个上下文只有原文有。

## Schema

**真源是 `schema.sql`，不在这里抄第二份。** 起草时这一节放过一份草案 SQL，等实现完成
它就立刻开始漂移（草案里还写着 FTS5、`topic_id NOT NULL`、7 种素材类型、核验状态有
「存疑」，全都和最终实现对不上）——同一件事有两处描述，迟早有一处是错的。

落地时和草案的实质分歧，以及为什么：

- **`topics.platform` 是单值列不是多选**。`draft.js` 早就用 `primaryPlatform` 收敛成
  只写主平台了，schema 应该说实话。想写第二个平台就新建一个选题。
- **`drafts.topic_id` 可空**。`/推` 产出的候选没有选题。
- **`task_key` 是 UNIQUE 列，不是正文标记**。幂等从「读回正文查字符串」变成数据库约束。
- **标签拆成关联表**，`tags` + `material_tags` / `inbox_tags`。
- **没有 FTS5**，理由见 `schema.sql` 末尾那段。
- **id 是 TEXT，UUID 与 ULID 共存**：迁移来的沿用 Notion page id，新建的用 ULID。
  这样迁移不需要 id 映射表，任何已经记下这些 id 的地方都不失效。
- **发布复盘是稿件表的一部分**（发布链接/时间、五个指标、反馈状态），
  加上素材表的 `draft_id` / `feedback_types` / `performance_basis`。
  草案漏了这一整块，因为它只出现在 `workbench.js` 的 `publishDraft` 里——
  **教训：迁移前必须把所有调用方读完再定 schema，漏一个文件就漏一组字段。**

## vault 布局

写进 `<你的 GitHub 用户名>/obsidian-vault`（**PRIVATE** 仓库，稿件是未发布内容，这点必须保持）的 `99 - 个人工作台/` 下。沿用 `workbench/server/lib/vault-dirs.mjs` 已经立好的规矩：01–04 是「你的字」，09 是机器抓的数据，中间留空号。

```
99 - 个人工作台/
├── 01 - 书架            （已有）
├── 02 - 洞察            （已有）
├── 03 - 稿件/           ← 由「03 - 归档」改名，本地尚未建过，零成本
│   └── 2026-08-14-公众号-写作复利.md
├── 04 - 网页批注        （已有）
├── 05 - 素材库/
│   ├── 01 - 核心观点/
│   ├── 02 - 金句/
│   ├── 03 - 数据/
│   ├── 04 - 案例/
│   ├── 05 - 框架/
│   ├── 06 - 反直觉点/
│   └── 07 - 个人经历/
├── 06 - 灵感/
│   └── 2026-08/
│       └── 2026-08-14-一条推特链接的标题.md
└── 09 - 热点            （已有）
```

**几个定死的规则：**

- **稿件一个目录管到底**，发布与否写在 frontmatter 的 `status`，**文件永不移动**。移动文件会断掉已建立的反链，而状态是会变的东西——用路径表达状态，等于让位置随状态漂移。
- **素材按类型分子目录**（你的选择）。类型目录带序号是因为它是固定的一组，不像书名那样无限增长；序号让文件树顺序稳定。注意 D1 里的类型值含 `/`（`金句/原话`、`数据/事实`），落到目录名要映射掉——`/` 不能做文件名。
- **灵感按月分**。它是流水，没有类型可分，只有时间。
- **文件名**：`YYYY-MM-DD-标题.md`，稿件多一段平台：`YYYY-MM-DD-平台-标题.md`。标题要清洗掉 `/ \ : * ? " < > |` 并截断（建议 40 字），重名加 `-2`。
- **Worker 只创建新文件，绝不修改已有文件。** 这是硬约束，不是建议——你的 Obsidian Git 插件每 1 分钟自动 commit、每 10 分钟 pull（`pullBeforePush: true`），只要两边不碰同一个文件，Git 自己就能合并干净。一旦 Worker 开始改写已有文件，就会和本地编辑撞车，而且是在你看不见的地方。

### frontmatter 与反链

三层内容用 wikilink 串起来，让「稿件 ← 素材 ← 灵感」这条链在 Obsidian 的关系图里能走通：

```yaml
# 05 - 素材库/02 - 金句/2026-08-14-复利需要时间不是强度.md
---
id: 01J8X...              # D1 的 material id，工作台反查用
type: 金句/原话
tags: [写作, 复利]
source: https://...
verification: 已核验
inbox: "[[2026-08-14-一条推特链接的标题]]"   # ← 指回原文
created: 2026-08-14
---
```

```yaml
# 03 - 稿件/2026-08-14-公众号-写作复利.md
---
id: 01J8X...
topic_id: 01J8X...
platform: 公众号
status: 待修改            # 发布后你改成「已发布」
materials:                # ← 指向实际用到的素材
  - "[[2026-08-14-复利需要时间不是强度]]"
created: 2026-08-14
---
```

**只写真实引用的素材**，标签检索来的补充候选不写进 `materials`——和 D1 里 `topic_materials` 只存真实关系是同一条原则，把「检索到过」和「真的用了」混为一谈，反链就失去意义了。

## 分阶段执行

每个阶段独立可验证、独立可回退。**不并行做两个阶段**——混在一起出问题时定位不了是哪块的锅。

模型保持现有的 `claude-opus-4-6-thinking` 不动。换模型是分发时才需要面对的事（别人得用自己的 key），归到阶段 4 的 README 里说明，不占一个执行阶段。

### 阶段 1：数据层换 D1（入口仍是 Telegram）✅ 已完成 2026-08-14

线上验证过的路径：Telegram 入库 → cron 初筛 → 建素材卡 → 打标签，以及工作台
全部 `/wb/*` 读端点（**工作台一行代码没改**）。实际改动比计划里更彻底，四处偏差：

- **砍掉 FTS5**。实测 trigram 分词对少于 3 字符的查询一律 0 命中，而中文最常用的
  就是两字词。原算法用标签词表匹配选题文本，本来就绕开了分词问题，保留即可。
  理由写在 `schema.sql` 末尾，别再有人「顺手补上 FTS」。
- **`drafts.topic_id` 必须可空**。`/推` 产出的候选没有选题，写成 NOT NULL 会让它存不了。
- **id 校验要认两种格式**。迁移来的是 UUID，新建的是 ULID，只认 UUID 的正则会让
  所有新建的东西「id 不合法」。
- **补上了发布复盘整块字段**（发布链接/时间、五个数据指标、反馈类型、表现依据）。
  初版 schema 漏了，因为它们只在 `workbench.js` 的 publishDraft 里出现，
  不读完那个文件就看不见——**这也是为什么迁移前必须把所有调用方读一遍**。


最大的一块。入口不动，这样出了问题一定是数据层的锅。

1. `schema.sql` 定稿 + `wrangler d1 create`
2. 写 `lib/db.js` 取代 `lib/notion.js`；删除全部字段辅助函数
3. 三个任务改写查询；`fetchSupplementary` 改成单条 SQL（含 FTS5）
4. 删除 `md2blocks.js`，移除 `@tryfabric/martian` 依赖
5. 幂等从正文标记改成 `task_log` / `task_key` 约束
6. **一次性迁移脚本**：把现有 Notion 四库的数据导入 D1，保留 id 映射
7. `/wb/*` 端点内部换实现，**对外契约一个字不变**

**验收**：`/run/{triage,synthesize,draft}` 三条路径跑通；工作台不改任何代码仍能正常读写；triage 一轮的 subrequest 实测降到 15 以内。
**回退**：Notion 数据保留只读，代码 `git revert`。

### 阶段 2：长文落 vault ✅ 已完成 2026-08-14

线上验证：素材/灵感已按目录落进 `<你的 GitHub 用户名>/obsidian-vault`，frontmatter 的 wikilink
反链正确，本机 Obsidian Git 正常 pull 到 Worker 写的文件、没有冲突。存量补写由
cron 自动跑（每轮 6 条）。

与计划的偏差：

- **补写做成了通用机制而不是一次性脚本。** `vault_path IS NULL` 同时代表「历史存量」
  和「上次写失败」——它们在库里长得一模一样，没有理由分两套代码。顺带让归档有了自愈能力。
- **顺序按引用方向**（灵感 → 素材 → 稿件），不是按数据量。被引用的先落地，
  补写过程中不会出现一段时间的空链接。
- 素材的 title 与 content 相同时只输出一次（`/金句` 存的素材都是这样）。


1. `lib/vault.js`：GitHub Contents API 写 `.md`，按上面的布局与 frontmatter 规则
2. `draft.js` 成稿后写 `03 - 稿件/`，D1 只留 `vault_path`
3. 素材创建时写 `05 - 素材库/<类型>/`；灵感初筛完成时写 `06 - 灵感/<月>/`（已弃用的除外）
4. 反链：素材 frontmatter 指回灵感，稿件 frontmatter 指向真实引用的素材
5. 目录与文件名约定**只写在 Worker 一侧**，通过 `/wb/*` 的 `vaultPath` 暴露给工作台

**需要的新密钥**：一个有 `<你的 GitHub 用户名>/obsidian-vault` 写权限的 GitHub PAT，存 wrangler secret。分发时这是别人要多配的一步，README 要写清 scope 怎么选。

**验收**：成稿后 vault 里出现文件、本地 10 分钟内拉到、Obsidian 关系图里能看到「稿件→素材→灵感」三层链路、工作台通过 `vaultPath` 能读到。
**风险**：与本地 Obsidian Git 撞车。缓解就是那条硬约束——只创建、不修改、重名加序号。

### 阶段 3：入口换飞书 ✅ 已完成 2026-08-14

线上验证：`/状态` `/整理` 走通，卡片拍板跑完整条 —— 点按钮 → 写平台+改状态 →
成稿（主料 3 条、补充料 9 条）→ 落库 → 归档 vault → 回执飞书。全程零错误。

与计划的偏差：

- **命令抽成了 `lib/commands.js`**，两个入口共用。原计划只说「命令平移」，
  照字面做就是抄一份到飞书那边——那正是 store.js 那条红线反对的事。
- **回执要认渠道**：job 参数从裸 chatId 改成 `{channel, chatId, idType}`。
  异步任务跑完时没有请求上下文，只有 payload 知道该回哪儿。
- **cron 必须带收件人**，否则每日 14:00 的卡片没有收件人，卡片拍板就只在手动
  `/整理` 时才有，等于白做。连带效果是成稿完成也会主动通知了。
- **回调地址不能用 `*.workers.dev`**（飞书推不到），绑了 `pipeline.example.com`。
  而配 routes 会默认关掉 workers.dev，必须显式 `"workers_dev": true`——
  否则会顺手弄挂 Telegram webhook 和工作台。
- 没做卡片点击后的原卡片更新。按钮留着是安全的，理由见 `lark-card.js` 的注释。


1. `lib/lark.js`：`tenant_access_token` 缓存刷新、消息发送、卡片构造
2. `lark-webhook.js`：URL challenge、AES 解密、`event_id` 幂等、3 秒内响应
3. 命令平移：存素材类、`/推` `/整理` `/状态` `/成稿`
4. **新增卡片拍板**：每日整理完推卡片，选题下挂平台按钮，点击回调直接带平台成稿——把"先写平台再改状态"那道闸门变成一个动作
5. 订阅 `drive.file.bitable_record_changed_v1` 之外的路径：状态变更由卡片回调触发，不再等 5 分钟轮询（cron 保留作兜底）

**验收**：飞书私聊全部命令可用；卡片按钮能触发成稿；重复推送不产生重复行。
**注意**：webhook 3 秒超时 + 重试 4 次（15秒/5分钟/1小时/6小时），现有"秒回受理 → Workflow 异步"的模式正好接得住，不用改架构。

### 阶段 4：合并仓库 + 分发化

## 未决问题

0. **`.dev.vars` 的 `TELEGRAM_WEBHOOK_SECRET` 和线上 wrangler secret 不是同一个值**
   （既有问题，非本次改动引入）。后果是 `/run/{triage,synthesize,draft}` 这条手动
   补跑/调试的路走不通，返回自己代码的 403。webhook 和 cron 不受影响。
   要修得重新 `wrangler secret put` 对齐。
1. **历史数据迁移的取舍**：全量迁移还是只迁"活着的"（未弃用的）？迁移时是否补写 vault 文件——几百条素材一次性 commit 进去，会在 Obsidian 里突然出现一大批文件。倾向：D1 全量迁，vault 只补写素材和已成稿的稿件，灵感不补写历史。
2. **`03 - 归档/发布作品` 的旧用途**：工作台 `routes/archive.mjs` 现在按「已发布」从 Notion 拉稿归档。改成稿件常驻 `03 - 稿件/` 之后，这个流程变成「改 frontmatter 的 status」，归档路由要一起改。属于工作台侧的改动，你那轮再动。
3. **飞书应用的形态**：自建应用需要企业管理员发布审批。你自己注册免费企业自批即可，分发时 README 要写清这一步。
4. **D1 免费版 500MB / 每次调用 50 次查询**——前者对纯文本绰绰有余，后者要在写批量 SQL 时留意（一次 invocation 里别循环发查询）。
