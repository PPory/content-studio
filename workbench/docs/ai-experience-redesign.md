## 一、执行摘要

### 结论一句话

**问题不是有太多聊天框，是这个产品没有「AI 结果类型」这一层模型，也没有把「AI 是什么」和「AI 长什么样」分开。**

所有 AI 产出——一句建议、一段正文候选、一份九问报告、一次要写盘的操作——最后都只能被压成
「聊天消息」或「一个弹层」。于是每加一种能力，唯一的落地方式就是**再加一个入口**。
21 个入口不是设计失控的原因，是这个缺失造成的**症状**。

### 数出来的现状

| 事实 | 数字 |
| --- | --- |
| 用户可触达的 AI 入口 | **19 个**（另有 2 个已不可达） |
| 并存的对话实现 | **3 套**（`AssistantPane` / `WritingAssist` 的「聊一聊」/ `CreationDialog` 的访谈） |
| 同一件事（写稿时找 AI 帮忙）的界面 | **2 套**，取决于你从哪扇门进来 |
| 同一批专家任务（`expertRun`）的入口 | **2 个**，标签 **3 套** |
| `quality-review` 这一个 kind 的显示名 | **3 个**：审稿建议 / 审一遍 / Xenho 品控九问 |
| 专家名单的真源 | **3 份**（`EXPERTS` / `PROJECT_EXPERTS` / `profile.experts`） |
| 风格选择器 | **2 处**，各存各的，互不同步 |
| 点了确实没反应的按钮 | **1 个**（阅读区右栏的「按建议改选区」） |
| 完全不可达的成品代码 | **~500 行**（访谈起稿、素材 AI 起稿两屏） |

### 五个最要紧的判断

1. **阅读区右栏有一颗死按钮**，而这个项目的第一原则就是「宁可不画，也不要画一个点了没落点的东西」。
2. **「写稿时的 AI 协作」有两套完全不同的界面**，能力还不一样——从项目页进和从稿件库深链进，看到的 AI 不是同一个 AI。
3. **AI 的「能力」和「呈现」在代码里是同一个维度**：`AssistantPane` 用 5 个布尔（`standalone` / `docked` / 有没有 `onInsert` / 有没有 `onRevision` / 有没有 `selection`）同时表达这两件事，32 种组合里 29 种没人验过——第 1 条那颗死按钮就是从那 29 种里漏出来的。
4. **336px 的项目右栏里塞着 4 个配置控件**（附件、权限、模型、风格），而它们全是「一年改一次」的东西，却和「问一句话」抢同一块地方。
5. **四类结果有四套视觉和四套采纳手势**，其中助手插入的候选没有「弃用」、检查报告的每条不能被处置、动作卡不能被拒绝。

### 目标结构

**能力由语义上下文和结果落点共同决定，呈现方式不参与能力判断。**

```
scope   = global | project | reading     AI 读什么、拥有哪些基础策略
target  = { kind, editable, ... }        结果落到什么对象、是否允许产生 Candidate
surface = page   | overlay | rail        AI 长什么样：占多大地方、配置露多少、怎么关
```

最终能力统一由 `resolveAssistantPolicy({ scope, target })` 推导；调用方不得传
`canInsert` / `canRevise` 一类能力判据。`surface` 只决定呈现，**不得增加或削弱能力**。
编辑模式也不等于 `project`：可编辑 vault 文档仍是 `reading`，不会因此获得项目阶段、项目素材或项目报告。

四种结果各有自己的形态、状态机和采纳手势：

```
回答/建议  → 消息流（唯一保留聊天形态的一类）
正文候选   → 候选卡：原文不动 + 可编辑 + 采纳/弃用 + 版本号 + 证据回执
检查报告   → 报告面板：三档严重度 + 每条能跳回正文 + 忽略/接受/去改（参考，不接闸门）
待确认操作 → 动作卡：说清影响 + 确认或拒绝 + 执行后回执
```

### 最终产品决定带来的四处方向改变

| 第一版方案 | 现在的决定 |
| --- | --- |
| 恢复访谈起稿与素材 AI 起稿两屏 | **不恢复**。访谈只通过通用 Skill 机制进入；素材起稿进入统一候选模型，删除前必须先把证据回执迁进结果模型 |
| dock 直接删掉 | **删 dock，但补一个全局召唤器**：顶栏按钮 + `Ctrl/⌘+I`，按当前页路由到项目栏 / 阅读栏 / 快速浮层 |
| 检查报告的 `blocking` 接上 `finish-writing` | **不接**。改成「高风险 / 建议修改 / 可选优化」三档，只作参考；发布闸门仍然只由服务端的确定性硬闸把守 |
| 编辑模式决定 `scope` | **否决**。`scope` 表达语义上下文，Candidate 能力与落点由 `target.kind` / `target.editable` 决定 |

## 三、每个入口的用户任务、作用域与能力

按十个核心问题逐个回答。为可读性合并成三张表，一行一个入口。

### 3.1 全局层（入口 1、2）

| 问题 | 回答 |
| --- | --- |
| 用户为什么来 | 跨项目思考、翻自己的 vault、问一个和当前页无关的问题 |
| 能读什么上下文 | 服务端挂载表（工作台项目 + vault + 显式授权目录）；**不读当前页面** |
| 能提出 / 不能改 | 能读、能检索、能联网、能提候选操作；不能静默写盘（`permission-modes.mjs` 服务端强制） |
| 结果类型 | 回答 + 待确认操作（`ActionCard`）。**没有正文候选**（`canInsert` 恒 false） |
| 与其他入口重复 | **1 和 2 完全重复**：同一个 `scopeId="global:assistant"`、同一份对话、同一套控件 |
| 高频操作是否被拖慢 | 是。每次都要看到「权限 日常」和模型名，而这两样几乎不改 |
| 结果采用后会发生什么 | 动作卡说清楚了（「新建到『创作』」等 11 种）✅ |
| task-first 还是空提示词 | **空提示词**。空态给三条起手句，但页面本身不知道你在做什么 |
| 技术信息压过内容 | 是。每条回复署名「Pi Agent SDK · gpt-5.6-terra · 0.2s」——运行时名字是最不重要的一条 |
| 符合「只提候选」 | ✅ |

⚠️ **1 和 2 的差别只有一条：dock 里没有历史侧栏**（`standalone && !docked`）。
也就是说**同一份对话，在两个地方打开，能力不一样**——而用户没有任何办法知道这件事。
这正是「用 5 个布尔同时表达能力和呈现」的直接后果。

### 3.2 项目层（入口 3–12）

| 问题 | 回答 |
| --- | --- |

| 高频操作是否被拖慢 | 是，严重。336px 的栏里有 4 个配置控件 |
| 结果采用后会发生什么 | 部分。插入说了「会带底纹，仍需确认采用」✅；但**「沉淀对话」没说卡片落在哪** |

## 五、按严重程度排序的问题

### critical

**C1 · 阅读区右栏的「按建议改选区」点了没反应。**

`SideRail.jsx:156` 用 `AssistantPane` 时传了 `selection`，没传 `onRevision`。
`AssistantPane:640` 的判据是 `canRevise={!standalone && !!selection?.text}`——只要划过词就为真，
按钮就画出来了；点下去走 `onRevision?.(…)`，`undefined`，**什么都不发生，也不报错**。

设计系统原文：「禁用的按钮比隐藏更糟——点不动又不说为什么，用户的结论是『这功能坏了』。」
一个**能点但没反应**的按钮比禁用更糟一档。

同一处还有第二个毛病：`SideRail` 没传 `standalone`，所以空态用的是**项目版文案**——
在一本书的章节里，右栏写着「这篇内容，下一步做什么？」「找出当前稿件最值得先解决的一处」。
那不是稿件，是别人写的书。

---

### high

**H1 · 「写稿时的 AI」有两套界面，取决于你从哪扇门进来。**

| | 项目页（`#/project/:id`） | 阅读覆盖层编辑模式 |
| --- | --- | --- |
| 组件 | `ProjectAssistantRail` | `WritingAssist`（`toolbarExtra`） |
| 有对话 | ✅ Pi Agent SDK，带会话 | ✅ `brainstormStream`，**另一套会话** |
| 有「想一想」一步推动 | ❌ | ✅ |
| 有「帮我写」续写/完成全文 | ❌ | ✅ |
| 有项目素材栏 | ✅ | ❌ |
| 有检查报告常驻 | ✅ tab | ✅ 弹层 |
| 有内联选区修订 | ✅ | ✅ |
| 风格选择 | 头部 select，不持久化 | 「帮我写」里的 select，存 localStorage |

两扇门都通向**同一批 `drafts` 记录**。用户不会知道「续写一段」这个能力只存在于其中一扇门后面。

**H2 · 项目对话没有历史，「新对话」是一次不可逆的清空。**

`refreshHistory()` 第一行是 `if (!standalone) return;`（`ProjectAssistantRail:268`）。
所以项目右栏永远拿不到会话列表，界面上也没有历史入口。
点「新对话」→ `conversationId = ""` + `messages = []`，上一轮从屏幕上消失。

而设计系统对「对话要能重开一轮」的原始理由是「一直聊下去上下文越滚越长也越跑越偏」——
那条理由成立，但它没说**旧的那轮必须消失**。standalone 那边有完整的归档/置顶/重命名/删除，
项目这边一个都没有。同一个组件两种记忆能力。

**H3 · 四种结果类型有四套视觉和四套采纳手势。**

| 结果 | 组件 | 形态 | 采纳手势 | 拒绝手势 |
| --- | --- | --- | --- | --- |
| 回答 | `Message` | Markdown 消息 | —— | —— |
| 正文候选（选区修订） | `RevisionReviewCard` | 编辑器内嵌卡 + textarea | 「采纳」 | 「弃用」 |
| 正文候选（助手插入） | `addAiDraft` decoration | 正文里的底纹 | 无显式采纳，靠保存 | **无显式弃用** |
| 检查报告 | `ExpertReport` | 报告块（rail 内）或弹层 | **无**（只能读） | **无** |
| 待确认操作 | `ActionCard` | 消息里的卡 | 「确认执行」 | **无拒绝按钮** |

**H4 · 336px 的项目右栏里有 4 个配置控件在和「问一句话」抢地方。**

`.project-workspace__grid` 右栏定宽 336px。而 composer 的 footer 里排着：
附件 `+` · 「权限 日常 ⌄」(`max-width: 160px`) · 模型名 ⌄ (`max-width: 220px`) · 发送。
仅后两个的上限就是 380px > 336px。头部还有第五个：「风格 · 原本语气」。

按 Emil UI 的频率规则：**权限模式和模型是低频决定，写稿求助是高频动作**。
把低频决定常驻在高频动作的输入框里，代价是每次打字前都要先看一眼四个和这句话无关的东西。

**H5 · 能力与呈现共用一个维度，32 种组合里 29 种没验过。**

`AssistantPane` 现在的参数面：`standalone` / `docked` / `onInsert` / `onRevision` / `selection`。
其中 `standalone` 一个布尔同时管着**四件互不相干的事**：
有没有历史侧栏、空态说什么、能不能插候选、`mode` 传 `general` 还是 `content`。

C1 和 H2 都是这个结构的产物，不是两个独立的疏忽。
`scope + target policy + surface` 的价值就在这里：**把语义上下文、落点能力和呈现拆开**，
组合数从 32 降到 9，其中真正用到的 5 种全部有名字。

**H6 · 全局助手页是一个不知道你在干什么的聊天框；而它的窄版复制品（dock）你几乎没用过。**

整页 100% 是对话流。没有任何地方回答：
- 它现在能读到哪些东西（挂载了哪些目录、vault 是哪个）；
- 我上次和它聊到哪（历史要点一下才展开）；
- 这台机器上还有哪些项目正在写（它明明读得到）。

dock 是这一页的窄版复制品，能力还少一块（无历史）。
**产品决定：删 dock，但「在任意页面不跳转也能调 AI」这件事必须留下**——
它不该由「把整页塞进右栏」来实现，而该由一个**召唤器**来实现（§7.1）。

**H7 · 访谈起稿与素材 AI 起稿不可达，而它们身上挂着真实性硬闸唯一的前端对应物。**

`CreationDialog` 的 `interview` 和 `material` 两屏（约 500 行）没有任何调用方。
⚠️ **产品决定：不恢复这两屏**——两者的能力搬进统一的项目助手（引导任务 + 素材候选）。

但**删之前必须先迁走一样东西**：`draftFromMaterials` 返回的 `skipped`，
以及围绕它的那句设计结论——**「悄悄剔除比不剔除更糟」**。
待核验的金句和数据不进稿，挑了 5 条只用了 3 条，不说的话用户的结论是「模型漏用了我的素材」，
而真正的原因和下一步（去核验）他一个都看不到。

这件事升级成结果模型里的一等公民：**证据回执**（§8.2）。
在证据回执落地并验收之前，**不许删 `CreationDialog` 的 material 屏**——
哪怕它现在进不去，代码里那段逻辑仍然是这条规则唯一的书面记录。

## 六、目标 AI 体验架构：scope + target policy；surface 只负责呈现

### 6.1 三个输入各管什么

**`scope` 管语义上下文与基础策略。** 它不等于编辑权限，任何 surface 都不能改：

| | `global` | `project` | `reading` |
| --- | --- | --- | --- |
| 读什么 | 挂载表（vault + 授权目录 + 库） | 这一篇：正文 + 阶段 + 素材 + 报告 | 当前文档 + 选区（+ vault 检索） |
| 基础策略 | **用户可配**（日常/创作/开发） | 项目事实 + 安全候选策略 | 阅读事实；不带项目阶段、素材和报告 |
| 基础结果 | 回答 · 操作 | 回答 · 报告 · 操作 | 回答（存笔记/存素材是用户动作，不是 AI 写入） |
| 会话归属 | `global:assistant` | `project:<draftId>` | `reading:<sourceKey>:<id>` |
| 模型 | 用户可选 | 继承全局 | 继承全局 |

**`target` 管结果落点。** Candidate 是否允许、落到哪里，由 `target.kind` / `target.editable` 决定：

```js
// 项目 Draft
{ kind: "draft", editable: true }

// 可编辑 vault 文档：仍是 reading scope
{ kind: "vault-document", editable: true }

// 总览、数据、设置等没有明确对象的页面
{ kind: "none", editable: false }
```

统一入口是 `resolveAssistantPolicy({ scope, target })`。调用方不得传 `canInsert` / `canRevise`；
可编辑 vault 文档可以获得明确落点的 Candidate，但不会因此获得项目能力。

**`surface` 只管呈现。** 它决定的事，任何 scope 都一样：

| | `page` | `overlay` | `rail` |
| --- | --- | --- | --- |
| 占地 | 整个 `.main` | 浮在当前页之上，不挤压 | 常驻侧栏 336px |
| 历史 | 常驻侧栏 | 一颗「最近」按钮 | 一颗「最近」按钮 |
| 配置控件 | 全展开（仅 `global` 有） | 收进「⋯」 | 收进「⋯」 |
| 关闭 | 换页 | Esc / 点外面 / 再按召唤键 | 收起按钮（状态存 localStorage） |
| 草稿 | 随会话 | **关掉不丢**（见 §7.1） | 随会话 |

### 6.2 实际用到的五种 surface 组合

```
global  × page     完整 AI 工作区（#/assistant）
global  × overlay  快速 AI 助手浮层  ← 新增，替代 dock
project × rail     项目协作区右栏
project × overlay  窄屏（≤1180px）时右栏的形态
reading × rail     阅读覆盖层右栏「AI 助手」页签
```

剩下四种组合（`project × page`、`reading × page`、`reading × overlay`、`global × rail`）
**不实现，也不留后门**——surface 组合仍是有限且被穷举过的；能力则统一交给 `scope + target policy`，
留一个没人验过的组合等于把 32 种布尔组合的问题按比例缩小地重演一遍。

### 6.3 一条必须写进代码注释的不变式

> **能力由统一的 `scope + target policy` 决定；`surface` 不得增加或削弱能力。**

具体到三条可测的断言：

1. `global × overlay` 和 `global × page` **共用同一个 `conversationId`**，
   在浮层里聊的每一轮都出现在完整工作区的历史里。
2. `scope: "reading"` + `target.editable: false` **永远不画候选类动作**。
   `scope: "reading"` + 可编辑 vault target 可以有 Candidate，但仍然没有项目阶段、项目素材和项目报告。
   ——C1 会由统一 policy 消灭，而不是依赖调用方记得传回调。
3. 权限与模型的可见性由 `scope` 决定，`surface` 只决定它们**收在哪儿**，不决定**有没有**。

4. `surface` 永远不出现在 `resolveAssistantPolicy` 的入参里。
### 6.4 三层各自回答哪句话

```
global    「我这一堆东西里，有什么关系是我没看见的？」
project   「这一篇现在缺什么，下一步写什么？」
reading   「这一句在说什么？」
内联       「这一句换个说法。」  ← 内联不是第四个 scope，是 project 的一种触发方式
```

⚠️ **内联刻意不是一个 scope。** 划词改写读的上下文、用的策略、产出的类型
和项目助手完全一致（都是 `project` 的候选），差别只在**触发点是选区、结果落在原地**。
把它单列成一层会立刻产生「内联的权限和项目的权限一不一样」这种没有意义的问题。

## 七、三类入口的信息架构

### 7.1 全局层：一个工作区 + 一个召唤器

#### 7.1.1 完整工作区（`global × page`，`#/assistant`）

**从「一个聊天框」改成「一块工作台 + 一条对话」。**

```
┌─────────────────────────────────────────────────────────┐
│ 顶栏面包屑：AI 助手                                       │
├──────────────┬──────────────────────────────────────────┤
│ 历史（常驻）  │  对话流（760px 可读列，居中）              │
│              │                                          │
│ ▸ 最近        │  ┌ 空态：不是三颗起手句，是「它现在能读到什么」┐│
│   · 复利那篇  │  │  vault: obsidian-vault（1,204 篇）      ││
│   · X 文风    │  │  项目: 3 篇在写 · 2 篇待复盘            ││
│ ▸ 已归档      │  │  授权目录: content-studio              ││
│              │  │  ───────────────────────────────────  ││
│ [+ 新对话]    │  │  三条起手句（保留）                     ││
│              │  └───────────────────────────────────────┘│
│              │                                          │
│              │  ┌ composer ───────────────────────────┐ │
│              │  │ 问任何问题…                          │ │
│              │  │ [+] [@专家] [/Skill]      [权限][模型]│ │
│              │  └─────────────────────────────────────┘ │
└──────────────┴──────────────────────────────────────────┘
```

- **历史侧栏常驻**，不再是一颗要点开的按钮。它是「我上次干到哪」——和全局检索空态同一条判据。
- **空态说清作用域**。这是 H6 的正解：不加功能，只把系统已经知道的事实摆出来。
- 权限和模型**只在这一层展开**，因为这是唯一需要它们的地方（产品决定 4）。

#### 7.1.2 全局召唤器（`Ctrl/⌘ + I`）

**一个键、一颗按钮，按当前在哪儿路由到不同 surface。**

```
按下 Ctrl/⌘+I（或点顶栏 AI 按钮）
   │
   ├─ 当前是项目页       → 展开并聚焦项目右栏 composer（不开浮层）
   │                       有选区时自动带上；已展开时只聚焦
   ├─ 当前是阅读覆盖层   → 切到右栏「AI 助手」页签并聚焦
   │                       有选区时自动带上
   └─ 其他任何页面       → 打开快速 AI 助手浮层（global × overlay）
```

**为什么是 `Ctrl/⌘+I`**（查过，不是挑的）：
- `MarkdownEditor` 只装了 `defaultKeymap + historyKeymap + indentWithTab`，**三者都不占 `Mod-i`**；
- 全局现有只有 `Ctrl+K`（检索）和裸键 `n`（入库），`Studio` 里另有裸键 `j/k//`；
- Chrome 在 Windows 上 `Ctrl+J` 是下载页、`Ctrl+I` 未占用，`--app` 窗口同理；
- 语义上和 `Ctrl+K` 分工清楚：**K 找已经有的，I 问还没有的**。

⚠️ **它必须在输入框里也生效**（和 `Ctrl+K` 同一条理由，和裸键 `n` 相反）：
写到一半想问一句是最主要的使用时机，要求先点出输入框等于砍掉一半用处。

#### 7.1.3 快速 AI 助手浮层（`global × overlay`）

```
                    （当前页面照常显示，不被挤压）
        ┌─ 快速 AI 助手 ────────────────────── 520px ─┐
        │ ⌘I 唤起 · 这是全局助手              [⋯] [×] │
        ├──────────────────────────────────────────────┤
        │ 带上了：热点 · 《…标题…》  [×]                │ ← 上下文条，可移除
        ├──────────────────────────────────────────────┤
        │  …多轮对话，和完整工作区同一条会话…            │
        │                                              │
        ├──────────────────────────────────────────────┤
        │ 问点什么…                                     │
        │ [+] [@]                    [在工作区继续 ↗]   │
        └──────────────────────────────────────────────┘
```

必须满足的九条（逐条对应产品决定 2）：

| 要求 | 落地 |
| --- | --- |
| 和完整助手同一个会话与后端 | `scope: "global"` → 同一个 `conversationId`、同一套工具与权限 |
| 对话进全局历史 | 由 `scope` 保证，浮层不做任何特殊处理 |
| 存在明确对象 | 上下文条只传页面类型、对象 ID、对象标题，并写明是哪一页哪一条 |
| 没有明确对象 | 显示「当前位置：数据 · 月度总览」+「未附带页面内容」；不得说「带上了页面」 |
| 允许移除上下文 | 上下文条右端一个 `×`，移除后这一轮就是纯全局提问 |
| **不自动隐式读整页** | 不发送页面数字、正文或 DOM。正文只在用户显式附带，或发问后由模型通过受控工具读取时进入上下文 |
| 不显示模型/权限/运行时 | 收进 `[⋯]`，且里面只有一句「继承全局设置 · 去改」 |
| 继承全局设置 | 同上 |
| 同一浮层内多轮 | 浮层不是「问一句就关」，Enter 发送后停留 |
| 「在完整工作区继续」保留同一 `conversationId` | 按钮跳 `#/assistant` 并带上 id；**不新开会话** |
| 关闭再打开不丢对话和草稿 | 会话由服务端持有；**输入草稿存内存 + `sessionStorage`**，按 `conversationId` 键 |
| 副作用仍走 ActionCard | 由 `scope` 保证 |

⚠️ **「不自动隐式读整页」这条要在代码里可测**，不能只是提示词里的一句话。
测法：在热点页唤起浮层、不发任何消息，断言请求体里**没有页面正文字段**。

⚠️ **浮层的定位与动效**：锚在顶栏那颗按钮上（不是视口中心），
`transform: translateY(-4px) scale(.98) → none` + `opacity`，180ms `ease-out`，
退出 140ms；`prefers-reduced-motion` 下只留 opacity。
Emil UI 的规矩：**anchored 元素必须从触发点长出来**。

### 7.2 项目层（`project × rail`）

见 §11 —— 那里给了两个候选方案的逐场景比较和推荐。

### 7.3 阅读层（`reading × rail`）与内联

**阅读层已经基本对了，只改三处：**

1. `scope: "reading"` 自动关掉候选类动作（消灭 C1），空态换成阅读版文案；
2. 页签名从「衍生 / AI 助手」改成 **「这一段 / 问它」**——
   边界靠**输入是选区还是整篇**自解释，不靠一句说明（M5 的正解）；
3. composer 里撤掉权限/模型（产品决定 4）。

**内联（`project` scope 的选区触发）：**

```
划词 → [润色] [纠错] [缩写] [扩写] [改写]  ← 保留，这是全产品最好的一处
        ↓
      候选卡（原文不动 + 可编辑 + 采纳/弃用 + 第 N 版 + 证据回执）
```

补三件：
1. **`WritingAssist` 的「想一想 / 帮我写」搬进来**——它们绑定的是光标，本来就属于这一层（H1 的正解）；
2. **助手插入的候选要有「弃用」**（H3）；
3. 正文为空时编辑器第一行一句灰字「划一段改写，或按 ⌘I 让它接着写」——空态引导，不是常驻按钮。

## 八、AI 结果类型与状态模型

### 8.1 四类结果

```ts
type AiResult =
  | { kind: "answer";    text: string }
  | { kind: "candidate"; target: Target; text: string; grounding?: Grounding }
  | { kind: "report";    findings: Finding[] }
  | { kind: "action";    type: string; impact: string }
```

**这四类的区别不是「长得不一样」，是「能对它做什么不一样」。**

| | 能采纳 | 能弃用 | 能重跑 | 能保存 | 会改正文 | 会改业务状态 |
| --- | --- | --- | --- | --- | --- | --- |
| answer | — | — | ✅ | ✅ 存笔记/素材 | ❌ | ❌ |
| candidate | ✅ | ✅ | ✅ | 采纳后随正文保存 | ✅ 采纳后 | ❌ |
| report | 逐条 | 逐条忽略 | ✅ 重查 | ✅ 存为笔记 | ❌ | ❌ |
| action | ✅ 确认 | ✅ **拒绝**（新增） | ❌ | — | 可能 | ✅ 执行后 |

### 8.2 证据回执（`Grounding`）——删除旧起稿流程的前置条件

这是从不可达的 `CreationDialog` 素材屏里**抢救出来**的那条规则，升级成结果模型的一部分。

```ts
type Grounding = {
  used:       { id: string; title: string }[]           // 用了哪几条
  skipped:    { id: string; title: string; reason: string }[]  // 跳过哪几条、为什么
  unverified: { quote: string; why: string }[]          // 正文里未经核验的信息
  gate:       "passed" | "rejected"                      // 服务端真实性硬闸的结论
  gateDetail?: string                                    // rejected 时的原因
}
```

**四条硬规则：**

1. **`grounding` 存在时必须在候选卡上可见**，`skipped` 和 `unverified` **不得默认折叠**。
   原文判据：「悄悄剔除比不剔除更糟」——挑了 5 条只用了 3 条，不说的话用户的结论是
   「模型漏用了我的素材」，而真正的原因和下一步（去核验）他一个都看不到。
2. **每条 `skipped` 必须带下一步**：待核验的 → `[去核验]`；不相关的 → `[仍然用它]`。
   一条只报告不给路的信息，等于把活儿推回给用户。
3. **`gate: "rejected"` 时候选不得进入 `ready` 态**，直接落 `failed` 并显示 `gateDetail`。
   前端**不得自己再判一次真实性**——判据只在服务端。
4. **在证据回执落地并验收之前，不许删 `CreationDialog` 的 material 屏。**
   哪怕它进不去，那段代码是这条规则目前唯一的书面记录。

### 8.3 状态机

**整篇正文候选（`target: whole-document`）**：

- 正文为空：允许生成 whole-document candidate。
- 正文非空：默认 UI 不提供「整篇起稿」，只提供续写、选区改写、补某一部分和结构建议。
- 用户明确要求「重写整篇」时不得静默降级。未来必须生成真正的 whole-document candidate，独立审阅并明确提示将替换全文。
- 审阅必须显示变更摘要、要求明确确认，采纳后支持一次产品级撤销。
- 在 whole-document 审阅能力实现前，不提供直接替换全文的操作。

**候选（candidate）**——最要紧的一条，因为它碰正文：

```
   generating ──→ ready ──→ adopted ──→ (undo 一次)
        │           │  ↑         
        │           │  └─ edited          用户可以先改再采纳
        │           ├──→ discarded
        │           └──→ stale            正文在此期间变了
        └──→ failed ──→ (retry)
             ↑
             └── gate: "rejected" 直接落这里
```

- `stale` 的判据已经有了（`documentVersion`），**要扩展到所有 candidate**，
  不只是助手消息——内联修订卡现在没有这个检查。
- `adopted` 之后底纹保留（`addAiDraft` decoration 已实现），
  但**必须给一条产品级撤销路径**：现在只能靠 CodeMirror 的 undo，那是编辑器的能力不是产品的承诺。

**报告（report）**——⚠️ **严重度改名，且不接闸门**（产品决定 3）：

| 档 | id | 显示名 | 含义 | 接闸门？ |
| --- | --- | --- | --- | --- |
| 1 | `risk` | **高风险** | 事实、数据、引用或第一人称经历可能不成立 | ❌ 不接 |
| 2 | `suggested` | **建议修改** | 结构、开头、口吻、逻辑上的问题 | ❌ |
| 3 | `optional` | **可选优化** | 更好但不改也行 | ❌ |

⚠️ **为什么不再叫「阻塞发布」**：设计系统里那条被反复兑现的教训——
「要加一道审查闸门时，先回答它有没有工具；**没有工具的闸门只是一个多出来的状态**。」
现在没有任何一条 AI finding 会影响 `finish-writing`，那就**不许用「阻塞」这个词**。
一个写着「阻塞发布」却挡不住发布的标签，是界面在说假话。

**真正的闸门仍然只有服务端那两道，一条都不动：**
- `draftReadyToFinish`（正文去空白后非空）——前端的 `blockedReason` 是它的可见对应物；
- `assertGroundedGeneratedText`（模型生成的个人经历必须有依据）。

以后若要给「高风险」加牙齿，前置条件是**服务端能确定性地判定它**，
而不是把模型的判断包装成一道闸门。

每条 finding 的状态：

```
   open ──→ accepted    （去正文改了）
        ├──→ ignored     （直接记，原因是可选字段——产品决定 5）
        └──→ resolved    （重查时发现已经不成立）
```

**重查时的行为**（产品决定 5）：
- 上次 `ignored` 的同一条 → 落进「之前已忽略 N 条」折叠区，**默认收起**；
- 只有**严重度升高**或**证据变化**时才重新拎出来，并注明「这次不一样了：…」。

**操作（action）**：

```
   proposed ──→ applied
            ├──→ rejected     ← 新增
            └──→ superseded   ← 已有
```

### 8.4 一条共享的呈现契约

四类结果共用同一个外壳，靠 `kind` 决定内部：

```
┌─ AiResultCard ──────────────────────────┐
│ ①标签行：类型 · 来源 · 时间 · [陈旧警告]  │
│ ②内容：kind 决定                        │
│ ③动作条：kind 决定，但位置永远在同一处    │
└─────────────────────────────────────────┘
```

**③ 的位置固定是这件事的全部价值**：设计系统里「动作条固定之后，
按钮永远在同一个位置，肌肉记忆才立得住」这条，现在只在 `SideRail` 内部成立，
四类结果之间不成立。

**关于「访谈」去哪了**（最终产品决定）：

访谈是实际注册的 **Skill**，不是产品内置任务。前端不增加访谈页面、Tab、专属按钮、`@访谈`、
专属会话或专属结果类型，也不硬编码 interview workflow；`@` 继续代表专家，`/` 代表 Skill。

用户可以用自然语言表达访谈意图，或通过通用 `/Skill` 选择器显式调用访谈 Skill。
如果运行时不能可靠地根据自然语言自动选择 Skill，只保证 `/Skill` 显式调用，不伪造自动调用。

访谈 Skill 自己负责一次只问一个核心问题、根据回答追问、不虚构经历、明确标记缺失信息、
任意轮次停止，以及整理共识或形成正文候选。Assistant UI 只认识统一结果：

```
对话过程             → kind: "answer"
最终共识或正文候选   → kind: "candidate"
```

Skill 名称可以作为普通运行状态元数据；渲染层不得出现 `if (skill === "interview")` 一类分支。

### 11.4 推荐：**方案 B**，加三条补丁

**理由按重要性排：**

1. **A 有一个规模天花板，B 没有。** 素材条数不受控，10 条时 A 必然崩，
   而两条补救路（自滚 / max-height）在这个项目里都已经被否决过。
2. **对话高度该是常数。** 用户在这一栏做的第一高频动作是问一句话、读一段回复。
   让这件事的可用高度随「这篇挂了几条素材」浮动，是把一个无关变量接进了主任务。
3. **A 的空态用 104px 说了两句废话**，而空态恰恰是新项目最常见的状态。

**代价与补丁**（不补的话 B 会把素材变成「消失的功能」）：

- **补丁 1 · 上下文条的每一段是可点靶子且带数字**，不是一行灰字。
  `在写 · 素材 4 · ⚠ 3`——三段各有 hover、focus 和按下态。
  一行灰字会让「素材」这件事在视觉上不存在。
- **补丁 2 · 素材面板浮在对话上方，不挤压对话。**
  插完素材通常紧接着就要回去写字，所以成本是「一次点开 + 一次收起」，可接受；
  若改成挤压式展开，就退化成一个会跳版面的方案 A。
- **补丁 3 · AI 结果卡里引用到的素材直接以 chip 显示在卡上。**
  「AI 用了哪几条素材」是最常问的一个问题，它不该需要展开面板才能回答——
  而这正好和证据回执（§8.2）是同一份数据。

**明确不做**：把上下文条做成可拖拽分割的两栏。
336px 是量出来的（素材行宽 + 中文对话可读性），给一个分割手柄等于把一个已经有答案的问题推回给用户。

## 十二、coss primitive 候选清单

⚠️ **前置事实：这个项目没有 Tailwind、没有 Base UI、没有 shadcn。**
`workbench/package.json` 里前端只有 React + CodeMirror + tabler icons；
样式全在 `src/styles.css` 一个文件（`design-system.md` 开篇写着「没有 CSS 框架、
没有 CSS-in-JS、没有 UI 库」）。

coss 装一个组件要带进 Tailwind v4 + Base UI + `data-slot` 约定，
这**直接撞上 `AGENTS.md` 的两条**：「不新增第二套设计语言」「不为了使用组件库进行大规模迁移」。

**所以本清单的用法是：把 coss 当作行为规范来对照，不当作依赖来安装。**

| 我们要的 | coss 对应 | 抄它的什么 | 项目里已有的 |
| --- | --- | --- | --- |
| 快速助手浮层 | `Popover`（不是 `Dialog`） | 锚定定位、非模态、Esc 与外部点击、返回焦点 | `use-dialog.js`（现在只做模态，需扩一个非模态分支） |
| 上下文条三段 | `Toolbar` | roving tabindex，一次一个 tab stop | `project-bar__end`（暂无 roving） |
| 素材面板 | `Popover` / `Collapsible` | 受控展开 + 可中断高度过渡 | 设置面板的「为什么」折叠 |
| `@任务` 选择 | `Command` | 搜索型面板键盘契约、`aria-activedescendant` | `assistant-command-menu`（自绘，已有上下键/回车/Esc） |
| 权限（仅全局层） | `RadioGroup`（不是 Menu） | 互斥语义 + 方向键 + `aria-checked` | `assistant-permission-menu`（已是 `menuitemradio`，语义已对） |
| 模型（仅全局层） | `Combobox` | 可搜索单选 | 同上 |
| 报告严重度 | `Alert`（`variant`） | **语气靠图标形状带，只有真出错才上色** | `ui.jsx` 的 `Note`——已经是这条规则的实现 |
| 右栏三段滚动 | `ScrollArea` | 只滚该滚的那一段 | `rail-panel` 三段结构——已实现 |
| 候选采纳/弃用 | `Button` + `AlertDialog` | 破坏性动作的确认语义 | `use-confirm-guard.js`——**比 coss 多做了一层**（320ms 防双击） |
| 检查进行中 | `Progress` / `Spinner` | 有分母才画进度，否则用不确定指示器 | `expert-progress` |
| 空态 | `Empty` | 空态必须给一个动作 | `rail-empty` / `assistant-empty` |
| 结果类型标签 | `Badge` | 状态用形状 + 浅底深字 | `.tag--state` / `.pill[data-tone]` |

**结论：12 项里 10 项项目已有等价实现**，其中 4 项（`Note`、`use-confirm-guard`、
`rail-panel`、`.tag--state`）比 coss 的默认行为更贴合本项目的判据。

**真正缺的只有两样**：
1. **非模态浮层的焦点契约**——`use-dialog.js` 现在只做模态（`inert` + 焦点陷阱），
   而快速助手浮层**不该是模态的**（它盖在页面上，但页面还能滚、还能点）。
   要按 `Popover` 的规矩扩一个分支：焦点不陷阱、Esc 关闭、返回触发元素、点外面关。
2. **`AiResultCard` 外壳**——没有对应的 coss primitive，那是产品自己的概念。

**本轮不安装任何 coss 组件。**

## 十三、ReUI 模式研究结果及采用理由

用 ReUI MCP 搜了任务书里点名的九类模式。结果如下（免费档，无 Pro license）：

| 搜索的模式 | 结果 |
| --- | --- |
| context-aware AI assistant | 0 免费，4 个 premium block（锁） |
| document copilot / assistant side panel | 同上 |
| resizable contextual panel | 0 免费，2 个 premium block（锁） |
| approval workflow | → `stepper`（免费） |
| activity / task timeline | → `timeline`（免费） |
| command / capability picker | → `autocomplete` / `cascader`（免费） |
| **diff / candidate review** | → **`code-block` + `c-code-block-22`「Patch review actions」**（免费） |
| review suggestions | → `alert` / `data-grid`（免费） |

### 13.1 唯一真正有价值的一条：`c-code-block-22`

> **Patch review actions — Agent-proposed diff with accept and reject actions.**
> `https://reui.io/preview/base/components/c-code-block-22`

这是本次检索里唯一**结构上正好命中我们缺口**的东西：AI 提出的改动 + 双栏 gutter +
接受/拒绝动作 + 变更摘要（`c-code-block-5` 的 "Diff with change summary"）。

**不采用这个组件，只采用它的信息结构。** 三个理由，按重要性排：

1. **我们的内容是中文散文，不是代码。** `code-block` 的核心是 Shiki 语法着色，
   对中文正文毫无意义，还会把等宽字体带进正文——而 `design-system.md` 里
   「等宽字体没有中文字形」是被记了整整一节的总根源。
2. **它需要 shiki + shadcn + Tailwind**，撞 §12 的同一条红线。
3. **我们已经有更合适的底座**：`MarkdownEditor` 的 CodeMirror decoration
   （`textRevisionField` / `addAiDraft` / `ai-draft-review.css`）能把候选**画在正文原地**，
   而 diff 视图是把候选画在**正文旁边**。原地更好——设计系统里
   「素材就地展开看全文，不弹层，因为看素材全文的目的就是对着正文看」是同一条判断。

**采用的具体三点**（写进 §8 的模型）：
- 变更摘要（`+N / −M`）：候选卡上现在只有「第 N 版」，没有「改了多少」；
- 拒绝动作与接受动作**同级同宽**：现在助手插入的候选根本没有拒绝；
- 逐行动作（`CodeBlockLineActions`）→ 我们的对应物是**逐条 finding 的动作**（去这儿改/忽略/找素材）。

### 13.2 `stepper` — 不采用

访谈流程看起来像 stepper（问答 → 共识 → 起稿），但它**不是**：
步数不确定（聊几轮由用户定），且不能跳步。
设计系统已经为此撤过一次七段流程线：「它画的是状态机，不是你的动线」。
按产品决定 1，访谈现在是项目助手里的一个任务，更没有理由给它一条进度轨。

### 13.3 `timeline` — 不采用，Defer（产品决定 6）

「一篇稿子上跑过哪些 AI」确实是一条时间线（3 次修订、2 次检查、1 次对话）。
但现在**没有任何地方存这个**（修订历史在 `/api/revisions`，
专家任务在 expert-runner，对话在 Pi 会话，三份不通）。
**产品决定：继续 Defer，不为它提前打通三套记录。** 本文不再为它保留待办位。

### 13.4 `alert` / `data-grid` — 不采用

报告的严重度分档我们已经有 `Note` + `.pill[data-tone]`，且比 `alert` 多一条
「形状是主编码，不辨色一样能用」。`data-grid` 是给几百行表格的，
一份报告十几条 finding 用不上排序、分页和虚拟化。

### 13.5 一句话总结

**ReUI 这次的收获是一个信息结构（patch review），不是一个组件。**
premium block 全被锁住这件事反而是好事——它逼着这次检索停在「模式」层面，
而模式正是 `AGENTS.md` 说的「先搜索 ReUI 是否已有成熟方案」真正想要的东西。

```js
export const ASSISTANT_SCOPES = {
  global:  { baseResults: ["answer", "action"], session: () => "global:assistant" },

export const ASSISTANT_SURFACES = {
  page:    { history: "sidebar", width: "column", dismiss: "route" },
  overlay: { history: "button",  width: 520,      dismiss: "escape" },
  rail:    { history: "button",  width: 336,      dismiss: "collapse" },
};
```

**关键：能力由 `resolveAssistantPolicy({ scope, target })` 算，调用方不能传，`surface` 也不在入参里。**
C1 那颗死按钮之所以能画出来，正是因为候选判据来自调用方漏传的 prop。
统一 policy 后，可编辑 vault 文档仍是 reading scope，但能按 target 获得明确落点的 Candidate；
只读阅读对象不会画候选动作。这些断言都进入纯函数单测。

**为什么不是一个混合 variant**（回答任务书那一问）：
`variant="reading"` 这种写法把「读什么」和「长什么样」又粘回了一起——
下次要做「阅读区的快速浮层」时，只能加第四个 variant 值，回到原点。
两个正交枚举的组合数是 3×3=9 且有明确的「实现五种、不实现四种」的清单；
一个混合 variant 的取值集合是开放的，没有边界。

### 14.3 要删的（全部排在最后，且各有前置条件）

| 删什么 | 前置条件 |

## 十六、验收标准

### 16.1 1366×768

| 检查 | 标准 |
| --- | --- |
| 项目页 | 主任务区无横向滚动；正文列 ≥ 660px；右栏 336px 不被压 |
| 项目右栏对话高度 | 空态 / 4 条素材 / 10 条素材三种情况**相同**（方案 B 的核心断言） |
| 项目 composer | 一行放得下 `[+] [@] … [发送]`，不换行 |
| 素材面板 | 浮在对话上方，**不改变对话高度**；超出时它自己滚 |
| 报告分栏 | 正文 ≥ 45%，报告 ≥ 320px，两者各自滚，**不套第三条滚动条** |
| 快速浮层 | 520px 宽，不挤压主内容，不遮住顶栏搜索框 |
| 全局工作区 | 历史 200px + 对话 760px 居中，两侧留白 ≥ 40px |

### 16.2 键盘

| 检查 | 标准 |
| --- | --- |
| 完整走通 | 建项目 → 写 → 划词改写 → 采纳 → 查一遍 → 处置一条 → 推进阶段，全程不碰鼠标 |
| `Ctrl/⌘+I` | 三种路由都对；**在输入框里也生效**；不与 `Ctrl+K`、裸键 `n`、`j/k` 冲突 |
| 焦点归位 | 每个浮层关闭后焦点回到打开它的那颗按钮（`use-dialog.js` 已有，新组件必须接上） |
| 快速浮层是非模态 | Tab **可以**走出浮层（它不是模态）；但 Esc 关闭、点外面关闭、焦点归位三条必须在 |
| Esc 分层 | composer 有内容 → 不关层；报告面板 Esc → 回正文；正文里打字时 Esc → 不退出 |
| 报告面板 | 打开时 Tab 不得走进背后的正文（这一层**是**模态，用 `inert`） |
| 无死键 | `@` 菜单开着时，方向键不冒泡到正文的 `j`/`k` |
| 上下文条 | roving tabindex，一次一个 tab stop，`←/→` 移动 |

### 16.3 焦点

- 采纳候选后，光标落在**被替换文本的末尾**，不是文档开头。
- 报告里点「去这儿改」，正文滚到那一处**并把光标放进去**，不是只滚过去。
- 候选卡出现时**不抢焦点**——用户可能还在打字（`RevisionReviewCard` 现在就不抢，保持）。
- 快速浮层打开时焦点进 textarea；关闭后回到顶栏那颗按钮（或按 `Ctrl+I` 之前的位置）。

### 16.4 加载

| 场景 | 标准 |
| --- | --- |
| Pi 冷启动 | 首屏 200ms 内出现「正在启动本机运行时」，与普通等待文案不同 |
| 流式 | 首字到达前不画空气泡（现有已做，保持） |
| 专家任务 | 说「第 N/M 条」；拿不到分母时用不确定指示器，**不画假进度条** |
| 素材推荐 | 骨架不跳版面；找完没有时说「通读完了」不说「失败」 |
| 报告面板 | 打开时正文位置不变（先量高度再分栏，避免版面跳一下） |
| 快速浮层 | 打开时即可输入，会话可以后到；不做「加载中不能打字」 |

### 16.5 错误

- 每条错误 = 真实 message + `hint`（下一步）+ 重试按钮。
- **重试保住用户输入**（现有已做）。
- 上游不可用与「结果为空」必须**长得不一样**：前者红，后者中性。
- 服务端拒绝的动作卡要说清**是哪条规则拒的**（权限模式 / 真实性硬闸 / 阶段闸门）。
- `gate: "rejected"` 的候选要显示 `gateDetail`，**不能只说「生成失败」**。

### 16.6 取消

| 动作 | 取消路径 |
| --- | --- |
| 生成中的回复 | `[停止]`（现有），停止后**保留已生成的部分** |
| 专家任务 | `[中止]`（现有），且关闭面板不中止（现有文案已对） |
| 候选卡 | `[弃用]` + `⌘Backspace` |
| 已采纳的候选 | **撤销一次**（产品级，不是只靠编辑器 undo） |
| 动作卡 | `[拒绝]`（新增） |
| 快速浮层 | Esc / 点外面 / 再按 `Ctrl+I`；**三条都不丢草稿** |
| Skill 引导任务（例如访谈） | 任意轮次退出，已聊内容不丢；统一 Candidate 可弃用 |

### 16.7 reduced motion

- 全局 `@media (prefers-reduced-motion: reduce)` 已有（`styles.css:5807`），**新组件不得绕开它**。
- 快速浮层：正常 180ms `ease-out` 从触发按钮长出；reduced 下只留 opacity，无位移无缩放。
- 素材面板展开：正常高度过渡 200ms；reduced 下瞬间展开。
- 窄屏右栏浮层：正常 280ms 位移；reduced 下直接出现。
- 流式打字**不是动画**，不受此规则约束（它是内容到达）。
- 候选底纹的出现**不做动画**——它是高频的，Emil UI 的频率规则：高频操作优先 immediacy。

### 16.8 真实性与硬规则（不可协商）

- 任何路径下，AI 都不得在用户确认前改动正文或业务状态。
- **`assertGroundedGeneratedText` 的前端对应物必须在用户看得见的地方出现**——
  在证据回执（§8.2）落地并验收之前，不许删 `CreationDialog.material`。
- **AI 检查报告不接发布闸门**；界面上不得出现「阻塞发布」这类它兑现不了的词。
- 发布闸门仍然只有服务端那两道；前端不得自己再判一次。
- 「已核验」不得由 AI 写入（`MaterialVerificationPanel` 现在是纯人工，保持）。
- 快速浮层**不得隐式把整页正文塞进请求**，且这一条要有断言。

---

### 16.9 阶段 1 专项

- 阅读区有选区但无 revision 落点时，不显示「按建议改选区」；空态只描述阅读任务，不称当前文档为项目稿件。
- `material-research` / `material-audit` / `quality-review` / `fact-check` 的 id、显示名与兼容映射只在 `lib/expert-kinds.js` 定义一次。
- 「沉淀对话」在打开确认层前说明保存对象与知识库落点；确认按钮再次写明写入位置。
- AI 报告只显示「高风险 / 建议修改 / 可选优化」，并明确报告仅供参考；不得出现「阻塞发布」或 `blocking` 的用户文案。
- 阶段 1 不修改 Worker / D1、Pi Agent SDK、硬闸、Assistant Core 或 `scope + target policy` 实现。

## 十七、已关闭的产品问题

Q8–Q11 已全部关闭；下面记录最终决定，不再保留待用户回答的分支。

### Q8 · 访谈入口——已关闭

- 访谈是 Skill，不是产品内置功能入口；不增加页面、Tab、专属按钮、`@访谈`、专属会话或专属结果类型。
- 用户用自然语言表达访谈意图，或通过通用 `/Skill` 选择器调用实际注册的访谈 Skill；`@` 只代表专家。
- 自然语言自动选 Skill 不可靠时，只保证 `/Skill` 显式调用，不伪造自动调用。
- Assistant UI 只渲染统一的 `answer` 与 `candidate`；Skill 名称只能作为普通运行状态元数据。

### Q9 · 整篇正文候选——已关闭

- 正文为空时可以产生 `target: whole-document`。
- 正文非空时，默认 UI 不提供「整篇起稿」快捷动作，只提供续写、选区改写、补某一部分和结构建议。
- 用户明确要求「重写整篇」时，不得静默降级成「续写一段」；未来必须产生真正的 `whole-document candidate`。
- whole-document candidate 必须独立审阅，明确说明将替换全文，显示变更摘要，要求用户明确确认，并在采纳后支持一次产品级撤销。
- 在上述审阅能力实现前，不提供直接替换全文的操作；这不是阶段 1 的实现范围。

### Q10 · reading / project scope——已关闭

`scope` 表达语义上下文，不由「是否编辑」决定；能力统一由 `resolveAssistantPolicy({ scope, target })` 推导。

```js
// 项目 Draft
{ scope: "project", target: { kind: "draft", editable: true } }

// 可编辑 vault 文档
{ scope: "reading", target: { kind: "vault-document", editable: true } }
```

可编辑 vault 文档不会因此获得项目阶段、项目素材或项目报告；`surface` 永远不参与能力判断。
调用方不得传 `canInsert` / `canRevise` 之类的能力判据。

### Q11 · 快速浮层的页面上下文——已关闭

没有明确对象的页面只显示：

> 当前位置：数据 · 月度总览
> 未附带页面内容

不得说「带上了页面」，也不得自动发送页面数字、正文或 DOM 内容。
存在明确对象时可以传页面类型、对象 ID 和对象标题作为引用。
正文只能在用户显式附带，或发送问题后由 AI 通过受控工具读取时进入上下文。
