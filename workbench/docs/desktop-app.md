# 当桌面应用用（开始菜单 / 任务栏）

`npm run app:install` 那一套的实现细节。**改 `scripts/launch.*` / `install-shortcut.ps1` / `make-icon.mjs` 之前先读这份**；
只改工作台前端和服务端的话，这里一条都用不上——所以从 `CLAUDE.md` 搬到这里。

---

`npm run app:install` 在开始菜单放一个「Xenho OS」，点它 = 确认服务在跑（不在就拉起来）+ 用 Chrome 的 **app 模式**开一个没有地址栏的窗口。任务栏独立图标、独立 Alt+Tab 项，用起来和别的应用没区别。装完在开始菜单搜「Xenho」，右键就能固定到任务栏。加 `-- -Desktop` 顺带放一份到桌面（默认不放：桌面有 tidy-desktop 自动归档，.lnk 迟早被扫走）；`-- -Uninstall` 删掉。除了那个 `.lnk`，**没写注册表、没装服务、没改系统设置**。

链路是 `.lnk → wscript → launch.vbs → powershell -Hidden → launch.ps1`。四层看着绕，每一层都在解决一个具体问题：

- **快捷方式指向 wscript 而不是 powershell**：指向 powershell 的话，即便带 `-WindowStyle Hidden` 也会闪一下黑窗——窗口是先创建再隐藏的。wscript 压根不创建。那一闪就是「这是个应用」和「这是别人拿脚本包了一层」的区别。
- **`launch.vbs` 必须是纯 ASCII**：wscript 按 ANSI 读 .vbs（除非存成 UTF-16），里面写中文就是乱码。
- **三个 `.ps1` 必须存成 UTF-8 **带 BOM**：powershell 5.1 不带 BOM 会把中文读成乱码。用 Write 工具改完这几个文件，**记得转一次编码**，否则界面上的提示全是问号。
- ⚠️ **主流程整个包在 `try` 里**。脚本是隐藏跑的，**没有控制台**，任何未捕获的异常都纯静默：点了图标什么都不发生，日志里也没有。踩过一次（见下条），查了两轮才想到去前台跑一遍 `powershell -File scripts/launch.ps1`——**这是排查这条链路的唯一办法**。
- **冷启动必须有启动画面**（`New-Splash`，黑底 + logo + 一行状态）。从点图标到界面出来有 2~10 秒，这段时间屏幕上什么都不变，人的反应一定是再点一次——于是起第二个进程抢同一个端口，`strictPort` 让它直接挂掉。启动画面不是装饰，是**挡住那个会把事情弄坏的动作**。超过 12 秒改口说「首次启动要预打包依赖」。
- **WinForms 用到才 `Add-Type`**：加载那两个程序集要将近一秒，而最常走的那条路（服务已在跑，直接开窗口）一个窗体都不用画。
- **dev server 的 stdout 重定向到文件，不用 .NET 管道**：Vite 每次热更新都写日志，管道没人读、满了就把服务卡死。日志在 `tmp/dev-server.log` / `.err.log`。
- **`WB_LAUNCHER=1` 让 `vite.config.mjs` 关掉 `open`**：不关的话它自己再弹一个普通浏览器标签，加上 app 窗口就是同一个工作台开两遍。手敲 `npm run dev` 时照旧自动打开。
- **窗口用 `--start-maximized` 直接铺满**，不再配 `--window-size`：两个一起给的时候尺寸会赢，窗口反而不是最大化的。开完还要人点一下最大化，就等于每次启动多一步。
- **端口从 `vite.config.mjs` 正则读出来**，不在 launcher 里抄第二份——`strictPort` 下抄错就是起不来。
- `app:stop` 只杀**命令行里同时含项目路径和 vite** 的 node 进程。按进程名杀会把这台机器上别的项目一起带走。

### 点叉号 = 应用真的关掉了（`server/lib/auto-exit.mjs`）

Chrome 的 `--app` 窗口点叉号**只关窗口**。后面那个 `node vite` 是 launcher 用 `-WindowStyle Hidden`
起的——没有窗口、没有托盘图标、任务栏上也看不见。用户以为关了应用，实际留了个常驻进程，
而唯一的收尾办法 `npm run app:stop` 藏在 package.json 里，界面上没有任何地方提过它。
每天点一次图标就多攒一个，直到重启机器。

所以 dev server 自己会在窗口关掉之后退出。三条闸缺一不可：

- **只认 `WB_LAUNCHER`。** 终端 `npm run dev` 绝不能退——开发时关掉一个浏览器标签就把服务带走，
  是在拿一个更烦的新问题换旧问题。要常驻（比如以后真做开机自启）就设 `WB_KEEP_ALIVE=1`。
- **连过一次才武装。** 服务刚起来时客户端数天然是 0，不设这条它会在浏览器还没打开之前
  就把自己关掉（`launch.ps1 -NoBrowser` 那条路必然踩中）。
- **有活在跑就不退。** 洞察周报和 Pi 后台任务可能要跑几分钟，不跟着某个窗口请求走。前台对话会由连接关闭事件取消；明确转入后台的任务则要等任务状态结束。

**判据是 HMR 的 WebSocket 连接数，不是 `beforeunload`。** 刷新页面也会触发 beforeunload，
而在断开那一刻，刷新和关窗长得一模一样；唯一能区分的信号是「过一会儿还有没有人连回来」，
那正是 HMR 已经在做的事。宽限期 4 秒，刷新的重连是毫秒级的，用户什么都感觉不到。

代价说清楚：**每次关掉都是冷启动**，下次点图标要等 2~4 秒（依赖已经预打包过，不是首次那 10 秒），
启动画面就是为这段时间准备的。换来的是任务管理器里不再有一串你不知道哪来的 node。

`npm run test:app-exit` 覆盖这三种情形：开着不退、刷新不退、关窗退。它不开浏览器，
直接拿 Node 内置的 WebSocket 冒充 HMR 客户端——这机制本来就只看连接数。

### 项目搬过家：`.lnk` 记的是绝对路径

`workbench` 从 `creator-workbench/` 搬进 `content-studio/` 之后，开始菜单那个图标还指着旧目录。**重跑一次 `npm run app:install`** 就改过来了（图标是生成物、不进 git，它会顺手重画一张）。两件不重跑就发现不了的事：

- ⚠️ **任务栏上固定的是 Windows 复制出去的一份独立 `.lnk`，不是开始菜单那个的引用**，重装改不到它。指着旧目录的固定项点下去是「什么都不发生」（wscript 找不到 .vbs）。所以 `install-shortcut.ps1` 发现上一次装的指向别处时会多打一段，提醒去取消固定再重新固定。
- ⚠️ **端口通了，不代表坐在上面的是这个目录的工作台**（`Get-PortOwnerRoot`）。旧副本还带着自己的 `node_modules` 和 `.env`，而端口是 strictPort 写死的 5180：它先起来的话，点图标打开的是**另一份**——界面一模一样、数据是另一份，**没有任何地方会说出这件事**，你只会觉得自己改的东西没生效。所以热启动那条路上先按端口反查占用进程的命令行、从里面切出项目根目录，对不上就明说是哪个目录占着、怎么停。
  - **只在认准了是别人的时候拦。** 切不出根目录（命令行长得不一样、拿不到进程信息）一律放行——宁可少拦一次，也不能让一个没见过的环境把启动器整个堵死。
  - 反查用 `Get-NetTCPConnection` + 按 PID 查 `Win32_Process`，不是复用 `stop.ps1` 那条「命令行里含项目路径」的筛法：那条回答的是「哪些进程是我的」，这里要回答的是「谁占着这个端口」，而且顺带拿到对方的路径才说得出下一步。

### 点图标起的进程，环境是**登录那一刻**的快照

从开始菜单点图标 → wscript → powershell → node，这一串的环境变量全部继承自 **Explorer**，而 Explorer 的环境是你登录时定下来的。**之后新加的用户变量，它一个也拿不到**（Windows 不会把变更推给已经在跑的进程）。

这件事炸出来的样子极具误导性，实际发生过一次：`workers.dev` 在这条网络上被 DNS 污染（解析到 `108.160.167.167` 这种完全无关的地址），必须走 `HTTPS_PROXY` 才通。`server/lib/fetch.mjs` 本来就认这个变量——**但只在它进得来的时候**。于是：

- 终端里 `npm run dev`：shell 是新起的，变量在，一切正常
- 点图标：Explorer 的老环境，变量没有 → 每个面板都是「连不上 Worker：fetch failed」

同一份代码、同一份 `.env`、同一台机器，两条启动路径两个结果，而**界面本身完全打得开**，只有数据是空的。

所以 `launch.ps1` 起 vite 之前**不读继承来的值**，直接问持久化的那几处：用户级环境变量 → 机器级 → `HKCU:\…\Internet Settings` 里的系统代理设置（勾了代理但没设环境变量的情况）。`NO_PROXY` 同理带过去。

> 加任何**要靠环境变量才能工作**的东西时，先想一遍：从开始菜单点进来的那条路上，它还在吗？在终端里验证通过**不能说明**图标那条路也通。

配套的是错误提示：原来写死一句「检查网络和 .env 里的 `WORKER_URL`」，而那次 `WORKER_URL` 完全正确，提示把人往错的方向引了。现在 `worker.mjs` 的 `connectHint()` 先说走没走代理（`proxyInfo()`）——走了就去看代理开没开，没走就知道是环境没带过来，两个方向都能立刻定位。

### 图标是现场光栅化的（`scripts/make-icon.mjs`）

从 `02--Resources/04--设计素材/logo-X字母黑底白色-20260812.svg` 生成 `scripts/xenho-os.ico`（生成物，跟着 `app:install` 自动跑）。自己画不引包：形状是**一个圆和一个方块的并集**（三圆角 + 右下直角），X 是**一条曲线都没有的多边形**（原 SVG 里全是 `L`），两样都是十几行数学，为它引一个带原生依赖的光栅化库，装的时间比画的时间长。颜色和 `index.html` 的 favicon 一致（`#111318` + 纯白 X）——任务栏和浏览器标签页都没有主题 token，这里就是写死的黑底白字。

⚠️ **不能所有尺寸都塞 PNG。** Explorer 从 Vista 起就认 PNG 帧，但 **.NET 的 `System.Drawing.Icon` 到今天都不认**——`new Icon(path, 64, 64).ToBitmap()` 会抛「Requested range extends past the end of the array」。启动画面要显示这个图标，第一版全 PNG，现象就是上面那条「点了没反应」。所以按常规布局来：**≤64 用 BMP（DIB，谁都认），128/256 用 PNG**（BMP 到 256 就是 256KB 一张）。BMP 帧要注意两点：高度字段写**两倍**（XOR 位图 + AND 掩码）、像素**自下而上**。启动画面另有一张 `xenho-os-64.png`，WinForms 直接 `Image.FromFile` 更省事。
