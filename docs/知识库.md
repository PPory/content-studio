# 知识库（本地 LLM Wiki）

工作台里用于沉淀长期认识、保留证据并在后续写作中复用的知识层。

**当前状态**：本地闭环已跑通。来源可从文件、公开网页、旧文章和正式发布稿进入；AI 只生成候选，用户确认后才写入词条；写作时由本地召回自动带回相关知识。

## 1. 采用了什么思路

借鉴 Karpathy 的 LLM Wiki：不在每次查询时重新阅读全部原始资料，而是把有价值的认识增量编译成可持续演化的 wiki。

本实现保留三件真正产生复利的事：

1. **归并**：新知识优先追加到已有词条，而不是反复新建同义页面。
2. **演化**：新旧说法可以并存、冲突或推翻，旧事实和旧定义不被覆盖删除。
3. **连接**：词条之间保存有方向、有含义的关系，并保留关系依据。

没有照搬飞书或 Markdown 文件式 wiki：

- SQLite 是唯一业务真源；Markdown 只用于导入导出。
- 全文索引和查询生成列表，不维护手工 A–Z 索引页。
- 关系由外键保证完整，反向链接通过查询得到。
- 本地单工作区优先，不承担跨设备同步。

## 2. 现役数据模型

```text
books / book_documents
  原始来源及不可变正文快照；保存作者、平台、原链接、发布时间、来源类型和内容指纹

entries
  词条当前名称、类型和定义；当前定义必须指向来源和逐字原文

entry_definition_revisions
  定义历史；每次修订保留来源、逐字原文、位置、内容指纹和原因

entry_facts
  事实行；保存来源、逐字原文、位置、内容指纹、事实时间和状态

entity_relations + entry_relation_evidence
  有向语义关系及其逐字依据

source_ingests
  来源提炼状态：queued / proposed / applied / rejected / empty / failed

action_candidates
  AI 提炼和体检产生的待确认候选
```

迁移顺序：

- `0006-wiki.sql`：词条和事实
- `0007-source-kind.sql`：来源归类
- `0008-source-ingests.sql`：提炼状态
- `0009-wiki-evidence.sql`：来源元数据、定义历史、事实与关系证据、完整候选状态

两个来源维度不能合并：

- `藏书 / 资料`：正文是否允许编辑
- `书籍 / 课程 / 文档 / 文章`：来源是什么

## 3. 完整链路

```text
文件、网页、旧文章、发布稿
        ↓
结构化来源 + 内容指纹去重
        ↓
提炼任务（只生成候选）
        ↓
逐字证据闸门
        ↓
人工审阅：默认整份接受，可取消个别错误项，或整份拒绝
        ↓
词条 / 定义历史 / 事实 / 关系 / 冲突
        ↓
本地召回、来源回看、孤儿与矛盾体检
```

### 来源入口

- **文件导入**：来源页支持书籍、课程、文档和旧文章；旧文章可记录作者、平台、发布时间、原链接和“本人创作”。
- **章节边界**：课程目录递归读取章节文件，一份文件就是一章，文件内部标题只作章内导航；文档和文章同样保持整篇。书籍格式仍可按书内目录拆章。
- **批量提炼**：来源页可选择多份来源，一次最多排队 20 节，并显示预计处理字符数。
- **公开网页**：AI 的 `propose_knowledge_source` 只提出“收进知识库”候选；用户确认后才抓取、入库和排队提炼。
- **正式发布**：发布成功后自动生成一次不可变的文章来源快照并排队提炼；重试不会重复生成。
- **对话沉淀**：用户明确要求“记住 / 沉淀 / 加入知识库”时，AI 先检索本地来源，再用 `propose_knowledge_update` 提出一条原子候选。普通问答不会擅自写入。

URL 只接受公开 `http / https`。原链接或正文内容重复时，在附件落盘前拒绝，不留下孤立资源。

### 证据硬闸

定义、事实、冲突和关系都必须带至少 12 字的逐字原文。服务端在候选生成后和对话候选确认时都会回到 SQLite 原文重新核对：

- 连续原文可直接通过。
- 用省略号连接多段真实原文时，每一段都必须分别存在。
- 没有标明省略却跳过中间内容、引用太短或原文不存在时直接拒绝。
- 原文内容指纹随证据保存，之后能判断来源是否变化。

逐字存在只能证明“引用没有编造”；它不能机械证明解释一定正确。因此审阅卡会把结论和原文并排展示，语义判断仍由用户确认。

### 审阅与审计

- 一份来源对应一张提炼卡，默认选择全部合格项，减少维护负担。
- 明显错误可逐项取消选择，不必因为一项坏结果拒绝整份来源。
- 接受和拒绝都会更新来源状态，并记录候选 ID、结果和人工决定。
- 定义更新不覆盖历史；事实冲突和推翻不删除旧事实。
- AI 体检只生成候选，不直接修改事实状态或建立关系。

## 4. 界面与使用

| 页面 | 路由 | 用途 |
|---|---|---|
| 词条 | `#/entries` | 审阅候选、查看健康指标、触发孤儿或矛盾体检、浏览词条 |
| 词条详情 | `#/entries/<id>` | 查看定义历史、事实、关系及每一条证据 |
| 书架 | `#/shelf` | 阅读 `source_kind = 书籍` 的来源 |
| 来源 | `#/sources` | 导入、筛选、批量选择、提炼或重试全部来源 |

桌面端体验要点：

- 来源可按未提炼、排队中、待审阅和失败筛选。
- 失败来源可直接重试，章节加载失败会明确显示。
- 词条健康指标可以直接进入孤儿或矛盾处理，不再只是静态数字。
- 点击定义、事实或关系的来源，会打开准确章节并高亮对应原文；取不到落点时不显示假按钮。
- 审阅卡显示模型、候选类型、结论、原文、冲突旧说法和关系理由。

本阶段按电脑使用设计，不以手机小屏幕为验收范围。

## 5. 检索与成本

写作召回使用本地 SQLite：

- 精确命中词条名和正文提及；
- 中文使用 2 / 3 字片段相似度补足“意思接近但没写词条名”的召回；
- 再沿已有关系补充邻近词条；
- 不调用嵌入模型，不产生额外联网成本。

提炼模型由 `AGENT_INGEST_MODEL` 控制；留空时跟随助手模型。可用 `AGENT_INGEST_BASE_URL` 和 `AGENT_INGEST_API_KEY` 单独配置提炼通道。模型质量以逐字证据丢弃率和人工审阅结果判断，不以产出数量判断。

## 6. 不能改坏的边界

1. SQLite 是唯一真源，不建立 Markdown 双向同步。
2. AI 只提候选；正式写入必须经过用户确认。
3. 定义、事实、关系和冲突没有来源逐字证据就不能进入知识层。
4. 系统状态、候选 ID、关系和内容指纹使用结构化字段，不能塞进正文。
5. 正式来源快照保持不可变；可编辑资料不能冒充不可变证据。
6. 发布回流、网页抓取和批量提炼可以自动排队，但自动排队不等于自动采纳。
7. 任何会写数据的测试必须使用系统临时目录中的独立 `XENHO_HOME`。
