# 知识库（本地 LLM Wiki）

工作台里「沉淀下来的知识」这一层。给下一个接手的人（或 Agent）看。

**当前状态**：能用，但只跑通了一条链的第一段。已入库 24 份来源 / 1389 节，
提炼过 20 节，产出 90 个词条 / 128 条事实 / 75 条关系。

---

## 1. 为什么做这个

工作台原来**只会堆积，不会复利**。素材、收藏、知识卡各自成岛，`entity_relations`
表建好了但一行没有。新存一条不会让已存的更有用，于是库越大越没人看。

参照 Karpathy 的 LLM Wiki（[原文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）：
不要每次查询都从原始资料重新推导，而是让 LLM **增量构建一个持久的 wiki**，
知识编译一次然后保持更新。

从第一性原理看，让知识**复利**而非**堆积**的只有三个操作：

1. **归并** —— 新事实落到已有词条上，而不是新建一页
2. **矛盾** —— 新事实和旧论断冲突时，冲突被记录而不是被静默覆盖
3. **连接** —— 两个原本无关的东西被链起来

⚠️ 网上流传的那套飞书实现（liucongg/llm-wiki-ops）**只做到了第 3 个**：它的 ingest
全是新建，唯一碰已有页面的动作是加一条回链。那样长出来的是**一本带链接的目录**，
不是会演化的综合体。本实现三个都做。

### 明确不抄的部分

| 那套实现的设计 | 为什么它需要 | 我们的情况 |
|---|---|---|
| 手工维护 index 文档 + A-Z 排序 | 飞书没有全文检索 | 有 FTS5。索引是**查询**，不是被维护的文档 |
| `wiki-binding.json` 存 node_token | 在跟飞书对象模型搏斗 | ULID 主键 + 外键，链接坏不了 |
| 「双链完整性检查」lint | markdown / 飞书链接会断 | `entity_relations` 有 FK + CASCADE，**断不了**，这条 lint 由构造消失 |
| Skill 这一层 | 豆包换个对话就不认识那个库 | AI 跑在应用进程里，给的是**常驻工具**，不用 @ 也不用记地址 |

**明确放弃**：跨设备。飞书在云上，这里是本地单机——选 local-first 时就付过的账。

## 2. 数据模型

```
entries          词条：id → entities, name UNIQUE, entry_kind, definition,
                       definition_source_id, orphan_since
entry_facts      事实：entry_id, statement, source_entity_id(NOT NULL/RESTRICT),
                       asserted_at, status(active|superseded|disputed),
                       superseded_by, conflicts_with
entity_relations 关系：复用已有表，relation_type 用语义值
source_ingests   哪些来源提炼过：status(proposed|applied|empty|failed),
                       model, rejected_ungrounded, error
```

迁移：`0006-wiki.sql`（词条层）、`0007-source-kind.sql`（来源归类）、
`0008-source-ingests.sql`（提炼状态）。

### 三个不能改坏的决定

**① 事实是行，不是 markdown 里的一行文本。**
那套飞书实现把事实写成 `- 内容（来源：文件名）`，来源是字符串——没法 join、没法
count、没法 diff。存成行之后每条事实可回溯原文，`verification_status` 那道真实性
硬闸也有地方挂。

**② 推翻和冲突都不删原文。**
那套实现在矛盾处写的是「以最新入库资料为准」，直接覆盖。那样「我曾经相信过什么、
为什么改了」就永久丢了——而对写作者来说，认知变化本身往往就是选题。

**③ 只存一条有向边，反向链接是查询。**
`entity_relations_to_idx (to_id, relation_type)` 已经建好，查入链是一个 query，
和正向永远不会不同步。

### 两个正交维度，别合并

- `books.metadata_json.kind` = **藏书 / 资料** —— 正文能不能改（引用可信度）
- `books.source_kind` = **书籍 / 课程 / 文档 / 文章** —— 这是什么（怎么归置和读）

一门课同样是只读的。合成一列的话「这门课能不能改正文」就没地方看了。

## 3. 链路

```
资料进来  →  提炼  →  审阅  →  体检  →  写作时召回
```

| 环节 | 代码 | 入口 |
|---|---|---|
| 本地语料导入 | `server/lib/corpus.mjs` | `scripts/import-corpus.mjs <目录> [--commit]` |
| 网页收进来 | `pi-tools` 的 `propose_knowledge_source` → `assistant-runner` 的 `knowledge_source_add` | 跟 AI 说「搜一下 X，存进知识库」 |
| 提炼 | `server/domain/wiki-ingest.mjs` | `scripts/wiki-ingest.mjs --book <书名> [--commit]`，或收资料后**自动排队**（`wiki.ingest` job） |
| 审阅 | `src/components/IngestReview.jsx` | 知识 → 词条，页面顶部 |
| 体检 | `server/domain/wiki-lint.mjs` | `scripts/wiki-lint.mjs [--only tension\|orphan] [--commit]` |
| 写作召回 | `workspace-domain.recallEntries` + `RelatedEntries.jsx` | 项目工作区右栏，自动出现 |

**所有 CLI 默认预演，`--commit` 才写。**

### 提炼的硬闸：逐字校验

⚠️ **这是整套东西最不能松的一处。** 「请标注来源」是一句提示词，模型可以照做也可以
敷衍，敷衍了没人看得出来。所以：**每条定义和事实必须附一段原文，服务端回原文逐字核对**，
对不上的直接丢并计入 `rejected_ungrounded`。

第一次跑就抓到一处编造（「笔记的三种作用」的依据在资料里根本不存在）。

闸门被真实文档修正过两次，两次都是**闸门自己的 bug**：

1. 模型用 `……` 拼接两段真实原文是**正当引用**，只做整串匹配会把它全判成编造
   （某模型因此被误杀 82%）→ 改成**按段校验，每段都要对上**
2. 比较时把空白压成一个空格，而中文段落之间是换行 → 原文变成「场景-情绪反应。 所以」，
   多了个任何模型都不会照抄的空格 → 改成**去掉全部空白**

**同时仍然拦住不加标记的省略**（模型会从「回顾/回忆。」直接跳到「（2）记录下」，
把中间几句吞掉）。测试在 `tests/wiki-ingest.mjs`，正反两面都钉住了。

### 确认的粒度：一次提炼，不是一条事实

Karpathy 说人类的 wiki 都会死，因为维护负担增长快于价值；而 `AGENTS.md` 第 4 条
要求 AI 只提候选。两条同时成立的唯一办法是把确认放在**一份资料**这个层面：
一眼看完它读出了什么，一次手势全接受或整张拒掉。逐条打勾的话维护成本回到人身上，
这个知识库照样会死。

## 4. 模型与检索

**提炼模型**：`AGENT_INGEST_MODEL`（留空跟随助手模型）。还可以整条换端点：
`AGENT_INGEST_BASE_URL` / `AGENT_INGEST_API_KEY`——助手那条通道会断配额
（实测一整批 19 节里 7 节挂在 `auth_unavailable`），而提炼是长跑。

**挑模型看逐字校验丢弃率**，不要凭产出好看与否判断。同一份资料实测：

| 模型 | 词条 | 事实 | 丢弃率 |
|---|---|---|---|
| **gpt-5.6-terra**（在用） | 8 | 12 | 0–21% |
| claude-sonnet-4-6 | 4 | 4 | 64% |
| gemini-3.1-pro-low | — | — | 该通道返回 HTML 错误页，用不了 |

Sonnet 的定义质量其实更好，但它倾向**改写**引文而不是照抄，改写过的引文没法回原文核对。

**检索**：`server/lib/web-search.mjs`，Tavily 优先、Brave 回落，
`AGENT_SEARCH_PROVIDER` 可强制。Tavily 每条结果带**正文摘录**（不是 meta description），
对「判断这份资料值不值得收」差别很大。回落时会报出实际用的是谁——静默回落会让
「这次结果怎么这么差」永远查不出来。

## 5. 踩过的坑（都是真事，别重蹈）

### ⚠️ SQLite 的 unicode61 不切中文 —— 这个坑栽了三次

整段汉字算一个 token。后果不是「少几条结果」，是**召回完全失效且不报错**：

1. **提炼时召回已有词条** —— 漏掉了已存在的「储存强度」，模型把它当新的又提了一遍，
   **归并整个失效** → 改成拿词条名去正文里做包含判断
2. **孤儿找候选** —— 8 个孤儿一个候选都召不回来 → 改成**同源共现**（事实引用过同一份资料）
3. **写作召回** —— 同样用名字匹配

**下次任何「按中文找相关」的需求，先假设 FTS 不管用。**

### ⚠️ 别用字符重合度找矛盾

先按「同词条 + 不同来源」配对再按二元组重合度过滤——两头都错：98 对里最高重合度
只有 0.19，阈值 0.22 等于全拦；而**方向是反的**，真矛盾（「A 提高记忆」对「A 没有效果」）
共享的词反而更少。重合度量的是话题相似度，不是冲突。

正确的单位是**一个词条的全部事实一起看**，成本也从 O(事实²) 降到 O(词条)。
已用植入的真假两组验证过：真矛盾抓得到，互补组安静。

### ⚠️ 候选动作类型漏登记会静默失败

`assistant-runner.mjs` 的 `normalizeProposedAction` 有一张类型白名单，不认识的返回 `null`。
加了 `knowledge_source_add` 却忘了登记时，**工具跟模型说「已提交」、模型跟用户说
「已提交」、库里 0 条**——整条链都在报成功。现在不认识的类型会 `console.warn`，
`tests/pi-runtime.mjs` 里也钉了一条断言。**加任何 `propose_*` 工具时记得登记。**

### ⚠️ 网页正文提取：base64 和导航壳

- 内联 `data:` 图片一个上千字符，会**骗过按字符数的长度检查**（实测抓回 9309 字符
  的导航壳，正文一个字都没有）→ 落地前剥掉
- 剥完还剩 677 字**真的菜单文案**，长度检查照样过 → 改成**结构判据**：有没有任何一行
  够得上段落（60 字）。阈值量过库里 1390 份真实文档：最长行中位数 267，
  而落在阈值下的恰是扉页、目录、书名页——它们本来就该被拦
- 判为导航就自动回落 Firecrawl。同一个 URL：**677 字菜单 → 49040 字真正文**

**导航树穿插在全文里，不是只在开头。** 实测那份 BytePlus 文档 1047 行里 787 行是导航
（侧栏被拍平进了 markdown）。掐头去尾完全无效。两层处理：

1. `stripNavigationLines` —— 按**链接占比**逐行删（导航行的字几乎全躺在链接里，
   正文行不会）。这是全文逐行，不是掐头
2. `trimToTitle` —— 用**页面自己的标题**定正文起点：正文里那一行是 `<title>` 的前缀。
   ⚠️ 是「正文行是标题的前缀」，不是反过来从标题里切主段——站点的分隔符五花八门
   （`|` `--` `–` `·`），猜分隔符要么漏要么切错

⚠️ **`excludeTags` 试过，没用**：这个站不用 `<nav>`/`<header>` 语义标签，导航项是
不带链接的纯文字，形状上和小标题一样。**别再往里加第七条形状规则**——
到此为止已经试过 onlyMainContent、excludeTags、剥 data URI、结构性垃圾判据、
掐头去尾、链接占比、标题锚点。同一个 URL 最终：81003 → 55686 字符，
开头是「This topic introduces prompting techniques…」。

剩下的少量噪音（`Copy Page` / `Feedback` 这类）没再追：提炼那一层有硬闸，
实测导航噪音一条都没变成词条。

### ⚠️ 「打开来源」跳错书

词条详情里每条事实都能点回来源，但接线时第二个参数写的是 `go("shelf", "resume")`——
「继续读最近那本」。于是点 Seedance 的来源会打开《结构化与知识管理》，而且没有任何提示。

⚠️ 事实只带 `source_entity_id`（一个章节 id），**跳转还需要它所属的书**。
现在 `entries/:id` 一并返回 `sourceBookId`，取不到时按钮直接禁用并说明原因——
「宁可不画，也不要画一个点了没落点的东西」。

### ⚠️ 词条名的两种脏

- **单字母**：模型把 INKP 拆成 I/N/K/P 各建一条 → 名字下限 2 字
- **粘着缩写字母的变体**：跑出「主题K」而库里已有「主题」（原文里 K 就是主题，
  作者的简写），两个词条定义几乎一样，然后它们之间还会互相「矛盾」
  → 剥掉尾部拉丁字母后等于已有词条就判为变体。**不能用「包含」当判据**：
  「概念笔记」包含「概念」而那是两个真概念

### ⚠️ 关系方向要在提示里写死

只给类型名，模型会产出 `行为经济学 example_of 损失厌恶`——而它自己的理由写的是
「损失厌恶是行为经济学研究的现象」。它知道事实，不知道字段从哪头读。
读法在 `values.mjs` 的 `ENTRY_RELATION_READINGS`。

## 6. 界面

| 页面 | 路由 | 职责 |
|---|---|---|
| 词条 | `#/entries` | 待审阅提案（顶部）+ 词条列表，按 kind 分组 |
| 词条详情 | `#/entries/<id>` | 定义 / 事实（每条可点回来源）/ 关系（双向） |
| 书架 | `#/shelf` | 只放 `source_kind = 书籍`，**读**的地方 |
| 来源 | `#/sources` | 全部来源的表格，**清点**的地方 |

导航结构：**知识**（一级）› 词条 / 书架 / 来源。书架从「发现」移了出来——
发现回答「东西从哪来」，知识回答「我已经有什么」。

几条界面判断：

- **来源页是表格不是封面墙**。封面对书是对的，但课程章节和文档导出没有封面，
  摆成墙就是一屏「加封面」占位框
- 来源表**列全部来源包括书**。排除掉最大的那部分（书占 90% 章节）等于不回答
  「哪些读过了、哪些真被用上」
- **有冲突的事实排在词条页最前面且不折叠**。藏进「更多」等于当它不存在，
  而那正是知识库慢慢烂掉的方式
- **写作召回一条一行**，定义和事实点开才出来。它是提示不是板块——
  上一版一条四行，把右栏上半屏吃掉还和「协作」的标题打架
- **召回的每条都要说自己为什么在这儿**（正文提到 / 连着谁）。不解释自己的推荐，
  用户看两次就再也不看了

## 8. 下一阶段

按优先级：

1. **界面上能触发提炼。** 现在只有 CLI 和「收网页时自动排队」两条路；
   来源页那 1244 节书没有任何界面入口去读。缺一颗「提炼这一份」的按钮。
2. **体检也要有审阅卡。** lint 现在只有 CLI，而它会改事实状态和关系——
   和提炼一样该走候选 + 确认。
3. **`stance`（我的主张）这一层还是空的。** schema 和提示都支持，但语料里
   只有一篇随笔是用户自己写的。要它长起来得先把用户发过的文章导进来，
   那才是「观点一致性检查」和「避免自我重复」能跑起来的前提。
4. **写→发→沉淀→下一篇的闭环没接。** `release_packages` 已经是实体，
   发布后自动进原始资料层并触发提炼，闭环就成了。
5. **提炼成本没有控制面。** 145 节全量提炼是笔真钱，目前没有预算提示或批次控制。
