# Content Studio「内容桥接」阶段决议

接着读：[`内容桥接-产品模型.md`](内容桥接-产品模型.md)（实验模型与边界）、[`内容桥接-实验验收.md`](内容桥接-实验验收.md)（第一版实际改动与验收）。

本文记录 2026-09-02 对下一阶段范围的判断，并**替代此前「Stage 10 = Smart Connection Discovery」的定义**。分支不变，仍是 `experiment/content-bridge`。

## 决议

把下一阶段从「智能连接发现」改为**「让桥的另一头有东西」**：先解决用户问题的供给，再谈连接发现。

连接发现本身是对的方向，但它的前提是两侧都有货。当前不是。

## 依据一：真实工作区的状态

截至 2026-09-02，`XENHO_HOME=D:/文档/Xenho` 的真实数据：

| 对象 | 条数 | 说明 |
| --- | --- | --- |
| Living Wiki | 100 | 284 条来源引用，概念 42 / 方法 52，内容真实 |
| Audience Problems | 1 | 手工录入的「创作焦虑」，无补充说明，`source_kind=manual` |
| Content Agendas | 0 | |
| Content Opportunities | 1 | 2026-09-01 保存 |
| 洞察报告（`knowledge_items` 中 `locator LIKE 'insight:%'`） | 0 | |
| `个人经历` 类型素材 | 0 | 素材共 31 条，类型只有框架/模型、核心观点、反直觉点、案例/故事 |

在 100 × 1 的库上做召回与重排，返回的永远是那一条。反方向（问题 → Wiki）能跑，但全库只有一个起点。**做完连接发现，内容机会数量不会变化，因为瓶颈不在匹配，在供给。**

## 依据二：用户问题这一侧没有供给管道

现役代码里，进入 `audience_problems` 只有两条路：手工录入，或 `POST /api/workspace/audience-problems/extract` 从洞察报告提取候选。

而洞察报告的生成器 `generateInsight`（`workbench/server/routes/local-support.mjs:65`）做的事是：取最近 12 条**本地素材**拼成一份 Markdown，标题为「本地内容洞察」。它不读取任何外部信息。`#/insights` 页面自己也写着「依据当前本地素材生成的内容洞察」。

于是这条链是断的：

```text
外部世界  →  （断）  →  洞察报告  →  问题候选  →  audience_problems  →  Bridge
```

`extractAudienceProblemCandidates` 要求每个候选携带报告中的逐字 `evidence_quote`。即使用户去生成一份洞察，报告内容也是创作者自己的素材——从自己的笔记里「提取别人正在困惑什么」，产出的 provenance 是假的。这个提取动作在当前供给下不应被鼓励使用。

结论：**Radar / 社媒洞察是真正断掉的那条链，但它是一个独立工程**（外部抓取 + 结构化 + 来源留存），不并入本阶段。

## 依据三：原稿明确给了不依赖外部抓取的供给方法

两份转写稿里有一条接手材料弱化了的判断：**议程可以反向生成选题**。

原稿原话大意是：确定了议程之后，就可以让 AI 把这个议程底下的一层问题全部拎出来，每一个都可以去讲，因此「就不再缺选题了」。

也就是说，Agenda 不只是「为什么持续讲、希望受众形成什么判断」这个战略层，它同时是**产生 audience problems 的种子**。这是当前唯一能在不依赖外部抓取的前提下，把问题库从 1 条做到几十条的路径。现役实现里 Agenda 只参与 `agenda_fit` 计算，没有这个生成能力。

同时，现役的新建议程入口埋在 Preview 结果的第 5 段（`ContentBridge.jsx:584`）——必须先选 Wiki、选问题、跑完一次 AI 才看得到。而按原稿，议程是**开始之前**就该确定的东西。0 条 Agenda 不是没用，是没地方建。

## 依据四：当前 Bridge 的入口顺序与原稿的真实动作相反

原稿描述的实际生产动作是：把群聊记录与自己和 AI 的聊天记录一起交给 AI，问「我们聊过的哪些知识，能解决大家共性的疑问」——**一次性给出两个库，让 AI 找出值得连的那一对**。

当前 Bridge 要求用户先做两次选择，AI 只做验证。所以「从验证器走向发现器」的方向是对的，但入口应当修正：不是「站在某个 Wiki 上找问题」，而是「什么都不选，直接问：我最近搞懂的东西里，哪些刚好能解释别人正在困惑的事」。

这一条记录在此作为连接发现阶段的设计前提，本阶段不实现。

## 本阶段范围

### 10a — 议程立到前面，并让它生成问题候选

- Agenda 可以独立于 Preview 创建、查看与修改，不再只作为 Preview 结果里的一个下拉项。
- 新增动作：从一个 Agenda 拎出「受众可能有的问题」候选。
- 输出是 Candidate，不直接写库；用户逐条确认后才进入 `audience_problems`。
- 候选必须写成「人正在困惑什么」，不是话题、不是标题。
- 来源如实记为议程推导，不得伪装成外部观察证据。
- 沿用现有 `content_agendas` / `audience_problems` / `audience_problem_sources`，不新建表。

### 10b — 随手记一个问题，摩擦降到接近零

真实的用户问题多数来自群聊、评论、私信，不来自周报。当前「自己记一个问题」只存在于 Bridge 页第二栏，等于要求用户先想起来去那儿记。

- 把「记一个用户问题」提升为 Ctrl+K 一级动作，可从任意页面直接录入。
- 录入路径保持轻：一句问题即可保存；来源与补充说明可后补。

## 明确不做

- **不做连接发现（原 Stage 10）**。推迟到问题库达到 30 条以上，届时按「依据四」的入口重新设计。
- **不重建 Radar / 社媒洞察**。单独排期。短期若需要外部问题，走「导入一份已有洞察报告」的入口，不在应用内重建抓取。
- 不为中文召回引入检索引擎。当前量级（100 Wiki / 1860 实体）本地全表匹配即可；已实测 `entity_fts` 的 `unicode61` 分词对中文召回严重不足（「焦虑」FTS 命中 14 条，`LIKE` 命中 81 条），而 FTS5 `trigram` 要求 ≥3 字，对两字中文词同样无效。这条留待连接发现阶段再定。
- 不迁移 Seeds / Ideas，不改 Series 语义，不重做 Today 主体结构。

## 附带发现（可单独修，不属于本阶段主线）

1. `createProjectFromOpportunity` 默认取整句 `coreClaim` 作项目标题（`workbench/server/domain/content-bridge.mjs:404`）。真实库中该项目标题是一句 60 余字的话，在 Today 与内容列表被截断。
2. 真实性硬闸只拦截伪造的 `experience` **要素**，不拦截 `experience` **主导动作**。真实库中唯一一条内容机会 `dominant_action=experience`，而 `个人经历` 素材为 0 条——系统推荐了一条用户执行不了的生产路径。应在推荐该动作时就提示缺少个人经历来源，而不是等保存时才拦。
3. ~~Bridge 页「最近保存的内容机会」卡片排版异常：核心判断后直接连排「创作焦虑9/1更新」，「已建立项目」掉到第二行。~~ 已修：`content-bridge.css` 里 `.bridge-head h2` 少一个右花括号，把后面 45 行规则全嵌进它的块里，那张卡的 flex 布局、省略号和状态胶囊一条都没生效。
4. Today 顶部仍是四张计数卡（本月发布 / 等你动手 / 可用素材 / 粉丝）。数量不是工作，下方「先做这一件」才是，计数卡应让位。
5. `内容桥接-实验验收.md` 的 API 清单与现役代码有出入：文档写的 `POST /api/workspace/{agendas,audience-problems,content-opportunities}/:id/archive` 实际是 `/:id/update`（以 `action` 区分 archive / restore）；清单亦缺少后续加入的 `POST /api/workspace/content-opportunities/agenda-fit`。
6. 真实库中那条内容机会的构造使用了 `source_kind: "wiki"`，而来源白名单是 `wiki_page`——它保存于加固提交 `ccfbf51` 之前，用现在的校验会被拒绝。属历史数据，不做迁移，记录备查。

## 验证要求

本阶段改动落地时按仓库既有标准执行：

```powershell
cd workbench
npm run check
npm run test:unit
npm run test:pi
npm run test:extension
npm run test:app-exit
npm test
npm run build
```

另需满足：

- 领域 → API → UI 的顺序，业务规则不下放到 React 页面。
- 议程生成的问题候选必须有 API 级副作用测试，证明 Preview 不写库。
- 持久化测试使用系统临时目录中的独立 `XENHO_HOME`，串行运行并清理。
- 真实浏览器验证 10a / 10b 两条路径，含空态、模型失败、刷新持久化与小屏。
- 每个阶段独立提交，不 push。

## 阶段完成判断

不以功能数量判断，以能否观察到下面这件事为准：

> 问题库从 1 条长到能支撑真实选择的规模，且其中的问题读起来是「人正在困惑什么」，不是话题或标题。

达成后再评估连接发现是否值得开工。
