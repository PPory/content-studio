# Content Studio「内容桥接」实验验收

## 实验边界

- 分支：`experiment/content-bridge`
- 安全基线：`2a7dcb8b482d7de969c92320005302fd107449f2`
- 业务真源：`XENHO_HOME/Workspace/workbench.db`
- 原则：AI 只生成候选；保存内容机会、创建项目、归档和其他正式写入都需要用户明确确认。
- 保留：Living Wiki、Raw Sources、Seeds、Ideas、Series、Content Project、现有写作与发布复盘链路。
- 未做：历史数据迁移、视觉关系图、热点自动成稿、评分排行、Today 重做、Assistant Runtime 重写。

## Before

原流程主要表现为：

```text
找题
→ 种子
→ 项目
```

用户容易从“找一个题”开始，把选题理解成标题或独立资源；Living Wiki 中长期积累的理解、Radar 中真实发生的问题，以及创作者想长期建立的判断，没有在项目创建前形成一条清楚的连接。

## After

实验流程变为：

```text
Living Wiki
      ×
Audience Problems
      ×
Agenda
      ↓
Content Opportunity
      ↓
现有 Content Project
      ↓
正文 / 版本 / 发布 / 复盘
```

用户可以从 Wiki 选择“我搞懂的”，从有来源的问题库选择“用户正在困惑的”，先得到问题、解释、认知差、核心判断、议程和内容构造，再决定是否保存。连接较弱时，系统会明确显示“不建议硬做内容”。保存后才可建立项目，项目继续沿用原有写作系统。

## Why

Content Studio 真正需要帮助创作者完成的，不是管理更多内容对象，而是发现：长期积累的知识能否解决真实世界正在发生的问题，并把这条连接构造成值得写的内容。

因此本实验把标题和成稿放到后面，把下面四件事放到前面：

1. 用户真正的问题是什么；
2. 我的知识能提供什么解释；
3. 最大的认知差在哪里；
4. 最终希望读者留下什么判断。

## 实际改动

### 新增表

| 表 | 用途 |
| --- | --- |
| `content_agendas` | 长期议程及希望受众形成的稳定判断 |
| `audience_problems` | 经用户确认的真实用户问题 |
| `audience_problem_sources` | 用户问题的逐条来源与证据文本 |
| `content_opportunities` | Wiki、用户问题、议程与内容构造的确认结果 |
| `content_project_opportunities` | 内容机会与现有 Content Project 的关系 |

这些表以增量 migration 加入；旧表与旧数据没有删除或迁移。结构化内容构造由服务端校验，不接受任意 JSON 字符串。

### 新增 API

```text
GET  /api/workspace/agendas
POST /api/workspace/agendas
POST /api/workspace/agendas/:id/update
POST /api/workspace/agendas/:id/archive

GET  /api/workspace/audience-problems
POST /api/workspace/audience-problems/extract
POST /api/workspace/audience-problems
POST /api/workspace/audience-problems/:id/archive

POST /api/workspace/content-opportunities/preview
GET  /api/workspace/content-opportunities
POST /api/workspace/content-opportunities
GET  /api/workspace/content-opportunities/:id
POST /api/workspace/content-opportunities/:id/archive
POST /api/workspace/content-opportunities/:id/project

GET  /api/workspace/projects/:id/content-intent
```

Preview 只接收引用 ID，由服务端读取 Wiki、Wiki 来源、用户问题、问题来源和议程。Preview 不创建内容机会、不创建项目、不改 Wiki、不改正文。

### 新增页面与组件

- `#/bridge`：新的 Content Bridge 工作区。
- `ContentBridge.jsx`：Wiki 与用户问题双侧选择、连接预览、议程选择、表达方式、入口、证据与反方、保存和建项目。
- `ContentIntentPanel.jsx`：项目顶部轻量展示用户问题、核心判断、支撑知识、议程、表达动作和证据缺口。

### 修改页面

- Living Wiki 详情增加“看看它能解决哪些用户问题”，进入 Bridge 并预选当前 Wiki。
- Radar 增加经确认用户问题列表与“看看我的知识能不能解释”，进入 Bridge 并预选当前问题。
- Project Workspace 接入独立创作意图组件，并优先提供挑战判断、找反例、找证据、换入口、换表达方式和检查议程等操作。
- 内容导航实验性收敛为“内容机会 / 创作 / 复盘”。

### 兼容 Route

- `#/ideas` 保留。
- `#/seeds` 保留。
- 两个旧入口退出主要导航，但仍可通过 Ctrl+K 访问。
- Seeds、Ideas、Series 及其数据语义没有改变；`content_series` 仍然只是合集，不承担 Agenda 语义。

## AI 与真实性边界

- strong、medium、weak 只表达三档判断，不生成伪精确分数。
- weak 或没有自然连接时允许明确建议更换知识或问题。
- 经历型没有真实个人经历来源时，只能给“如果你有类似真实经历”的条件式入口。
- 经历要素缺少来源 ID 时，服务端拒绝保存。
- 大众入口必须携带范围检查；承诺超过正文能力时标记“范围过大”。
- 事实、证据、反方、Agenda 匹配和假设边界保存在 Candidate 中，只有用户确认后才写入正式机会。

## 已知限制

1. 第一版只给现有洞察增加“提取用户问题候选”的结构化动作，没有重写整套社媒洞察 Skill。
2. Agenda 已具备完整本地域和 API，Bridge 可以选择现有 Agenda；单独的 Agenda 管理界面不在本轮核心场景内。
3. Radar 只把经用户确认的 Audience Problem 交给 Bridge，不把原始热点标题直接当问题。
4. 没有迁移 Seeds、Ideas 或历史选题数据；替代旧心智的效果仍需真实使用验证。
5. Today 没有增加机会数量提示，避免核心场景稳定前扩大首页改造。
6. 浏览器验收使用临时 SQLite 与确定性的 AI Candidate；服务端 Preview 契约、模型失败、真实性和副作用边界由独立 API 测试覆盖。
7. 生产构建仍有原有主包超过 500 kB 的提示，本实验没有扩展范围做全局拆包。

## 后续建议

1. 先用真实 Wiki 与已确认用户问题连续使用一段时间，观察 weak 判断是否可信、Opportunity 是否真的减少“为了写而写”。
2. 根据真实使用再补 Agenda 管理界面和 Radar 的结构化机器消费层，不提前扩展更多一级对象。
3. 只有核心路径稳定后，再评估 Today 的轻量提醒与 Seeds / Ideas 的长期迁移方案。
