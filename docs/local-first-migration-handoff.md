# 本地优先单工作区迁移

  ## 一、最终结论

  工作台改为完全本地优先：

  - 工作台编辑器仍是唯一主要编辑入口。
  - SQLite 是唯一业务真源。
  - 图片、图书、附件保存为本地文件，由 SQLite 记录关系。
  - AI 助手、浏览器插件、定时任务全部读取本地工作区。
  - 不再依赖飞书、Supabase、D1、Worker 或 Obsidian。
  - 保留通用 Markdown 导入导出，但不绑定 Obsidian。
  - 暂不打包 Electron，保持现有本地启动方式。
  - 只维护一个现役工作区，默认位置为系统“文档”目录下的 Xenho。
  - 通过稳定 ID、领域接口和版本化导出格式，为以后迁移到服务器保留通道。

  目标目录：

  Documents\Xenho\
  ├─ Workspace\
  │  ├─ workspace.sqlite
  │  ├─ workspace.json
  │  └─ assets\
  │     ├─ images\
  │     ├─ books\
  │     ├─ attachments\
  │     └─ imports\
  ├─ Backups\
  └─ Exports\

  SQLite 适合作为单机应用文件，具备事务、跨平台和长期兼容性；运行中的数据库必须通过 Backup API 生成一致性快照，不能直
  接复制可能仍有 WAL 的文件。SQLite 应用文件格式、SQLite Backup API、WAL 说明。

  本计划正文就是交接文档。当前仍处于计划阶段，没有修改项目；执行对话应在基线提交完成后，将本计划保存到 docs/local-
  first-migration-handoff.md。

  ## 二、目标架构与数据规则

  ### 本地服务分层

  - workbench/server/domain/：业务规则、状态变化、真实性校验和用户确认规则。
  - workbench/server/storage/：SQLite、资源文件、事务、迁移和搜索实现。
  - workbench/server/jobs/：本地持久任务队列。工作台运行时执行，关闭期间错过的任务在下次启动补跑。
  - 前端统一调用本地 /api/workspace/*。
  - 扩展继续使用 /api/extension/*，保留配对、离线队列和重试机制。
  - AI 通过领域工具查询和提出候选，不直接修改数据库、正文或文件。
  - 最终删除 /api/pipe/*、Worker 代理和其他旧兼容入口，不长期保留两套架构。

  新增内部接口固定为：

  - WorkspaceRepository：事务、实体读写、关系、搜索、软删除。
  - AssetStore：导入、去重、读取、校验、导出本地资源。
  - JobStore：入队、领取、幂等执行、失败重试和启动补跑。
  - BackupService：创建一致性备份、校验、暂存恢复和切换。

  ### 数据模型

  SQLite 至少覆盖：

  - 收集、种子、素材、标签。
  - 创作项目、正文、平台版本、项目素材关系。
  - 发布记录、数据快照、复盘。
  - 图书、批注、网页批注和知识内容。
  - 正文修订历史。
  - AI 会话、消息、附件和已确认操作。
  - 资源文件索引。
  - 本地任务、执行记录。
  - 工作区设置。
  - 导入批次、逐项结果和迁移审计。

  固定规则：

  - 正文使用 Markdown 文本；状态、关系、任务信息不能写进正文。
  - 迁移时保留原有 ID；新记录继续使用 ULID。
  - 删除先进入回收站，以 deleted_at 表示，不直接硬删除。
  - SQLite FTS5 负责本地全文搜索。
  - 资源按 SHA-256 去重，内部正文使用稳定的 asset://<asset-id> 引用。
  - 导出时再将资源引用改写为相对路径。
  - 不恢复已经退出产品的“每日计划”栏目。
  - 项目是创作主线；选题候选在用户确认创建项目前不成为独立业务项目。

  ### 备份、导出与导入

  提供两种产物：

  1. .xenho-backup：完整恢复包，包含一致性 SQLite 快照、全部资源、清单和哈希；排除 .env、密钥、缓存与日志。
  2. .xenho-export.zip：可迁移包，包含 Markdown、frontmatter、CSV、JSONL、资源和版本化 manifest。

  同时保留普通 Markdown 文件夹导入导出，但不依赖 Obsidian 目录结构。

  恢复必须先在临时工作区完成：

  - 校验 manifest 和文件哈希。
  - 运行 integrity_check 与 foreign_key_check。
  - 验证版本和记录数量。
  - 先备份当前工作区，再原子切换。
  - 重启服务后重新读取验证。

  自动备份采用“启动后补跑”：超过24小时未备份时，在下次启动创建一次；保留最近7个日备份、4个周备份以及所有迁移前备份。

  ## 三、实施阶段

  ### 阶段0：保护当前未提交成果

  - 检查 feat/ui-circle 的所有已修改和未跟踪文件。
  - 不允许 reset、stash、覆盖或混入迁移代码。
  - 完成现有 UI、编辑器和 AI 改动的验证。
  - 为现有改动创建独立基线 commit；若无法确认某项改动归属，停止并报告。
  - 基线完成后，保存本交接文档并创建迁移计划 commit。

  ### 阶段1：建立本地存储基础

  - 引入并锁定适配 Node 22 的 better-sqlite3。
  - 实现工作区路径解析、schema migration、事务、外键和 FTS5。
  - 实现内容寻址资源库、回收站、导入审计和工作区元数据。
  - 所有测试使用系统临时目录中的独立工作区，禁止触碰真实 Documents\Xenho、真实 vault 或 .xenho。

  ### 阶段2：迁移业务规则和本地任务

  - 将 Worker 中仍然有效的状态、发布、幂等、素材关系和真实性硬闸迁入本地域层。
  - 删除已经过时的栏目和流程，不照搬旧 D1 表。
  - 将定时任务改成本地持久任务；工作台启动后检查并补跑。
  - 保持“AI 只提出候选，用户确认后才执行”的边界。

  ### 阶段3：切换工作台、AI 与扩展

  - 页面数据源全部切换为本地工作区 API。
  - 正文自动保存、修订、图片插入、书架、素材和发布复盘写入本地。
  - AI 搜索并读取 SQLite、正文、素材、图书、附件和历史会话。
  - 浏览器扩展的收集、批注、状态和离线补传改为本地写入。
  - 服务继续只监听 127.0.0.1:5180，保留临时配对令牌。
  - 不增加 Electron、手机端或云同步。

  ### 阶段4：完整数据迁移与切换

  先对快照排练，成功后再冻结旧系统写入并正式迁移。来源优先级固定为：

  - D1：现有结构化业务记录的权威来源。
  - 工作台本地文件和浏览器状态：发布数据、指标、修订、阅读状态等本地专属内容。
  - .xenho：AI 会话、附件和执行历史。
  - Obsidian：仅迁移 99 - 个人工作台 中没有其他权威来源的图书、知识、批注、网页笔记和媒体。
  - Supabase：仅作为已引用媒体原件的来源；影子业务表只用于核对，不覆盖 D1。
  - 飞书：不做整库导入，只检查已映射文档。若飞书内容比本地更新或哈希冲突，停止并提供差异，由用户决定版本。

  迁移报告必须包含：

  - 各来源记录数量。
  - ID、关系和正文哈希。
  - 图片、图书和附件的数量、大小、哈希与缺失项。
  - 冲突、跳过、去重和失败项目。
  - 迁移前后逐类对账结果。

  只有正式迁移、重启读取和完整验收均通过，才能解除旧系统只读状态。

  ### 阶段5：备份、导出导入与恢复验收

  - 完成完整备份、自动轮换、手动导出、导入预览、冲突处理和恢复。
  - 用真实数据快照的副本进行一次完整恢复。
  - 将可迁移导出包导入新的空工作区，对比数量、ID、正文哈希、关系和资源。
  - 图书原文件包含在完整备份中；便携导出默认只带笔记和元数据，用户选择后才包含图书原件。

  ### 阶段6：清理代码和项目知识

  本地架构验收后：

  - 从活动代码中移除 worker/、supabase/ 以及飞书、D1、Worker、Supabase、vault 专用路由、库、测试、配置和环境变量。
  - 删除 WORKER_URL、WORKBENCH_KEY、SUPABASE_*、FEISHU_*、VAULT_ROOT 等旧设置。
  - 保留模型配置和密钥在本机 .env，不进入备份、导出、Git 或日志。
  - 更新 README、根规则、workbench/CLAUDE.md、工作流、设计文档和环境变量示例，使 SQLite 本地工作区成为唯一现役答案。
  - 删除过期的飞书同步规则、旧迁移说明和云端架构说明；历史由 Git 保存，不在现役文档中继续干扰。
  - 已跟踪旧代码通过 Git 删除，仍可从历史恢复；归属不确定的散落产物先移入 .tidy-trash/<日期>/ 并生成 MANIFEST，最终确
    认后再清除。

  - 运行一次完整项目知识收尾，确认代码、运行时、文档和规则一致。
  - 每个阶段创建独立 commit，不 push。

  ### 阶段7：删除外部资源

  先提交“最终删除清单和恢复点报告”，再次取得用户明确确认，然后才执行：

  - 删除项目专用飞书知识空间及同步文档。
  - 删除项目专用 Supabase 项目及 Storage 数据。
  - 删除项目专用 D1 数据库。
  - 下线项目专用 Cloudflare Worker、路由、Webhook 和定时触发器。
  - 撤销对应 Token、密钥和授权。
  - 仅清理 Obsidian vault 中经过绝对路径核验的 99 - 个人工作台；不得删除整个 vault、其他目录或 Obsidian 程序。
  - 删除前为该目录生成可恢复归档并核对哈希。

  删除后验证云端资源和端点已经不存在，同时在断网、无旧环境变量条件下再次运行本地工作台。

  ## 四、验证与完成标准

  执行以下现有检查：

  cd workbench
  npm run check
  npm run test:unit
  npm run test
  npm run test:writing
  npm run test:pi
  npm run test:extension
  npm run test:app-exit
  npm run build

  另外必须完成：

  - 从收集、种子、素材、项目、正文到发布复盘的完整流程。
  - 有效和无效输入、外键、事务回滚、回收站和重复导入测试。
  - 图片插入后检查实际文件字节、重启显示、导出及重新导入。
  - AI 能读取迁移后的正文、素材、书籍、附件和历史会话。
  - AI 修改正文、业务状态、文件或执行副作用操作时仍要求用户确认。
  - 扩展在真实 Chromium 中完成连接、收集、批注、离线排队、重启补传和 AI 调用。
  - 自动任务补跑且重复启动不会重复写入。
  - 完整备份恢复和便携导出重建均通过对账。
  - 关闭旧服务、移除旧环境变量并阻断旧网络端点后，工作台仍完整可用。
  - 搜索活动代码和文档，不再存在有效的 D1、飞书、Supabase、Worker、Obsidian/vault 依赖。
  - 验证当前开始菜单/本地启动方式仍然有效。
  - git diff --check 通过，工作树无遗留迁移文件。

  最终完成条件：

  - 全部栏目、正文、素材、图书、资源、发布数据、AI 历史和阅读状态可在重启后读取。
  - 迁移清单中的数量、哈希、关系和资源均完成对账。
  - SQLite 和本地资源目录成为唯一真源。
  - 备份可恢复，导出可重建。
  - 浏览器扩展继续工作。
  - 活动代码、配置、文档和规则只描述本地架构。
  - 外部资源仅在最终确认后删除并完成删除后复验。
