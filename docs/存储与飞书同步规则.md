# 存储与飞书同步规则

> 这是可演进规则，不是一次性定死的部署图。项目还在快速变化时，先保持接口边界稳定，
> 再分批替换底层存储；任何一次迁移都不能同时改变业务规则、正文格式和编辑体验。

## 一句话架构

```text
工作台编辑器 ─┐
              ├─ 飞书：正式正文
飞书编辑器 ───┘

业务接口 ── 当前 D1 ── 目标 Supabase：用户、项目、关系、状态、同步映射、AI 任务
附件 ───── Supabase Storage；需要独立大文件层时才启用 R2
本地 ───── Obsidian：原书、私人知识、单向归档
```

当前阶段不直接把 D1 整库替换成 Supabase。先让 `/wb/*` 契约继续作为唯一业务入口，
完成飞书正文闭环；等项目字段和流程稳定后，再把接口背后的 D1 一次性迁到 Supabase。
迁移完成后停用 D1，不长期双库运行。

## 真源规则

每一种数据只能有一个正式来源：

| 数据 | 正式来源 | 其他副本的性质 |
| --- | --- | --- |
| 稿件、洞察、知识卡片等可编辑正文 | 飞书文档 | 工作台编辑态与 AI 索引都是可重建缓存 |
| 项目、阶段、关系、权限、发布记录 | 当前 D1，未来 Supabase | 不写进正文，不由飞书反推 |
| 原书、私人阅读资料 | 本地目录 / Obsidian | 用户逐本选择是否上传云端 |
| 图片、PDF、音视频等附件 | 默认 Supabase Storage | R2 只在流量、成本或独立性需要时启用 |
| 人类可读归档 | Obsidian | 单向导出，不反向覆盖线上正文 |

飞书正文不能再在数据库中保存另一份同等地位的正式正文。为了搜索和 AI，可以保存切片、
摘要、向量和最近缓存，但必须标明它们是派生数据，并能够从飞书重新生成。

## 双编辑器同步规则

1. 工作台打开已绑定稿件时，读取飞书最新版；临时编辑只存在当前编辑会话。
2. 工作台保存时，先比较“上次同步摘要、当前工作台摘要、当前飞书摘要”。
3. 只有工作台变化：允许推送到飞书。
4. 只有飞书变化：先展示飞书版本，再由用户确认同步回工作台。
5. 两边都变化：进入冲突，不自动覆盖；用户选择保留工作台、保留飞书或人工合并。
6. 第一次同步：创建飞书文档，数据库只记录稿件 ID、飞书 token、链接和两端摘要。
7. 自动同步失败不能阻止本地编辑；界面必须显示未同步或失败原因。
8. 图片、评论、画板等不可无损重建的飞书块存在时，禁止全文覆盖，后续改为块级更新。

第一阶段只开放“人工触发同步”，不做后台自动覆盖。等真实使用确认冲突体验后，再考虑事件订阅。

## AI 助手规则

- AI 通过工作台内容接口读取项目关系，通过飞书接口读取最新正文，不直接遍历数据库。
- 回答和分析可以自动读取；修改正式正文必须形成候选并由用户确认。
- 飞书暂时不可用时，可以读取带时间戳的最近缓存，但必须提示内容可能不是最新版本。
- AI 索引命中后，生成答案前应再次读取对应飞书文档，避免使用过期切片。
- 系统任务 ID、同步摘要、权限、状态等技术信息禁止写入飞书正文。

## 书架规则

- 书名、作者、标签、阅读状态等结构化信息进入业务数据库。
- 原始 PDF、EPUB、扫描件默认只在本地，尤其是版权书籍和私人资料。
- 书摘、读书笔记和生成的知识卡片可以进入飞书，并归档到 Obsidian。
- 用户可以逐本选择“允许云端使用”；选择后才上传私有 Storage 并建立 AI 索引。
- 云端书籍必须支持私有权限、临时访问链接、删除原文件及删除派生索引。

## 飞书权限

首个闭环采用用户身份，只申请：

- 创建、读取、更新云文档；
- 读取、创建、更新知识库节点；
- 需要长期登录时使用离线授权。

文档写入指定知识空间时，该用户或应用还必须是空间成员。机器人消息权限与文档权限分开，
不因为已有机器人就默认拥有知识库访问权。

## 演进与验收

每个阶段只改变一层：

1. 飞书单篇创建、读取、更新、拉回与冲突检测；
2. 工作台界面提供人工同步和冲突对比；
3. AI 检索改为从飞书读取最新版；
4. 稳定业务字段后迁移 D1 到 Supabase；
5. 再决定是否启用自动同步、Supabase Storage 或 R2。

每阶段必须至少验证：工作台写入飞书、飞书修改后可预览拉回、两端同时修改不会静默覆盖、
权限不足给出明确下一步，以及重新启动后映射关系仍然存在。
