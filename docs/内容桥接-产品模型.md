# 内容桥接：产品模型与实验边界

## 实验基线

- 分支：`experiment/content-bridge`
- 本地基线：`2a7dcb8b482d7de969c92320005302fd107449f2`
- 基线来源：执行任务时最新且工作区干净的本地 `feat/wiki-entries`
- 设计依据：现役工作流、Living Wiki、架构、AI 协作与设计系统文档，以及 `docs/` 下两份转写原稿

本实验不锁定旧版本，不迁移旧数据，不改变 SQLite 作为唯一业务真源的地位。两份转写原稿只读保留。

## 一句话目标

Content Studio 的核心不是帮助创作者管理更多内容对象，而是帮助创作者发现：

> 我已经搞懂的东西，刚好能解决谁正在困惑的问题。

第一版只验证这一条路径：

```text
Living Wiki：我已经搞懂了什么
        ×
Audience Problems：用户正在困惑什么
        ×
Agenda：我希望受众长期形成什么判断
        ↓
Content Opportunity：一个值得继续构造的内容连接
        ↓
现有 Content Project：写作、版本、发布与复盘
```

## 当前模型

现役主路径是：

```text
反应 → 种子 → 项目 → 发布 → 复盘
```

其中“种子 = 触发物 + 我的判断”能够承接即时反应，但“找题 / 选题”仍容易让用户把创作理解为先找一个标题，再补观点与素材。Living Wiki 已经形成长期、可追溯的知识；Radar 和洞察已经保存外部信号；两者尚未在一个明确流程里连接起来。

## 新模型

### 我搞懂的

来自 Living Wiki，表示已经形成、可复用、可追溯的知识和理解。继续使用现有 `wiki_pages`、版本、来源、链接和操作日志，不建立第二套知识库。

### 用户的问题

来自 Radar、洞察报告、帖子、评论、反馈或用户手动记录。它不是热点标题，而是能够回到具体来源的真实困惑，例如“模型越来越多，我到底应该追哪个？”

### 内容机会

内容机会是某个 Wiki 知识能够解释某个用户问题的候选连接。它先说明问题、解释、认知差与核心判断，再讨论怎么表达；它不是标题、评分排行或自动稿件。

### 长期议程

议程描述创作者希望持续表达后，受众逐渐形成的稳定判断。议程不是分类，也不是合集：

```text
Series / 合集 = 内容怎样组织和呈现
Agenda / 议程 = 为什么持续讲，以及希望受众形成什么判断
```

二者允许多对多地服务同一创作方向，但本实验不改变 `content_series` 的现役语义。

### 内容项目

只有用户保存内容机会并明确建立项目后，才调用现有 Content Project 领域能力。正文、版本、素材、平台版本、发布、数据和复盘继续沿用现役系统。

## 为什么改变

两份转写稿给出了三个关键判断：

1. 选题不是可被“找到”的既有资源，而是反复选择和组织后的结果。
2. 同一组内容要素，因为关系结构或主导表达动作不同，会成为完全不同的内容。
3. 深知识可以通过大众正在困惑的问题进入，但入口承诺必须由后续内容真正兑现。

因此，本实验不再把“生成几个题目”作为中心动作，而把“知识能否自然解释一个真实问题”作为中心判断。

## 内容构造模型

选题的内部结构是：

```text
内容要素集合 × 要素关系结构 × 主导表达动作
```

### 内容要素

第一版限制在：概念、事实、案例、经历、判断、问题、证据、方法、类比、冲突、观察。它们只存在于内容机会的内部结构，不升级为新的一级资源或页面。

### 关系结构

第一版支持：因果、类比、对比、冲突、支持、挑战、概念到案例、案例到抽象、问题到机制、机制到方法。关系用于 AI 分析、服务端校验与持久化；前台只显示用户能直接理解的叙事步骤，不开发视觉关系图。

### 主导表达动作

只使用四种：

| 值 | 前台名称 | 核心动作 |
| --- | --- | --- |
| `knowledge` | 知识型 | 解释一个概念或机制 |
| `judgment` | 判断型 | 提出并论证一个判断 |
| `experience` | 经历型 | 用真实个人经历展开 |
| `demonstration` | 展示型 | 通过过程、结果或现场展示 |

同一个知识底座在不同问题、关系与动作下可以形成真正不同的内容。

## 增量数据模型

本实验新增：

- `content_agendas`：长期议程；核心字段是 `desired_judgment`。
- `audience_problems`：经过用户确认的问题。
- `audience_problem_sources`：问题与 Radar、报告、帖子、评论、反馈或手动来源的证据关系。
- `content_opportunities`：知识、用户问题、可选议程与内容构造的已确认连接。
- `content_project_opportunities`：已保存机会与现有项目的关系。

继续保留：

- `seeds`；
- ideas/topics；
- `content_projects`；
- `content_series`；
- Living Wiki 全部现役表；
- Raw Sources 的不可变证据原则。

第一轮不删除、不改造、不迁移这些旧对象。

## 核心字段语义

### Agenda

- `title`：简短名称。
- `audience`：主要服务对象。
- `problem_space`：长期帮助用户解决的问题。
- `desired_judgment`：希望用户长期形成的判断，是最核心字段。
- `value_commitment`：持续为用户提供的价值。
- `related_product`：可空，不强制商业化。
- `status / archived_at`：现役状态与软归档。

### Audience Problem

- `statement`：用户用自然语言表达的困惑。
- `summary`：为什么值得关注。
- `source_kind / source_ref`：主要来源回执。
- 多条 `audience_problem_sources` 保存具体证据、观察时间与来源对象。
- AI 只能提出候选；用户确认后才保存。

### Content Opportunity

- `wiki_page_id`：支撑知识。
- `audience_problem_id`：被解释的问题。
- `agenda_id`：可空的长期议程。
- `core_claim`：内容最终要留下的判断。
- `knowledge_explanation`：该知识能提供的解释。
- `cognitive_gap`：大众现有理解与候选判断之间的差异。
- `dominant_action`：四种主导表达动作之一。
- `fit`：只允许 `strong / medium / weak`。
- `fit_reason`：连接为何成立或不成立。
- `construction_json`：经过服务端 Schema 校验的要素、关系、入口、证据缺口与反方。
- `status / archived_at`：已保存机会的生命周期。

## AI 协议与边界

内容桥接复用 Assistant Core，并增加 `scope = content_bridge`；不创建第二套助手或运行时。

`POST /api/workspace/content-opportunities/preview` 只接受 Wiki、Audience Problem 与可选 Agenda 的引用 ID。服务端读取 Wiki 正文与来源、问题与来源、议程，再调用 AI。浏览器不拼接完整知识正文。

AI 可以：

- 判断连接强弱，包含明确的“不自然连接”；
- 区分表层问题和深层问题；
- 解释知识、提出认知差与核心判断；
- 建议表达动作、内容要素、关系、大众入口、证据缺口与反方；
- 检查入口承诺是否超出正文能回答的范围；
- 判断与议程的适配度。

AI 不可以：

- Preview 后自动保存机会或创建项目；
- 自动写回 Wiki、正文或业务状态；
- 把假设升级为事实；
- 没有来源时生成第一人称经历；
- 为了产出结果强行连接无关对象；
- 生成爆款概率、精确机会分或标题排行榜。

### 真实性硬闸

`experience` 只有在工作区存在用户笔记、项目日志、明确保存的经历或其他可核验 provenance 时才能生成具体第一人称候选。没有依据时只能提示“如果你有类似真实经历，可以从这里进入”。事实、数字、引语和来源同样由服务端校验，不能只依赖提示词。

### 大众入口 Scope Check

每个入口必须同时回答：“这个入口承诺的问题，后面的内容是否真的能够回答？”不能兑现时标记“范围过大”并缩小，不把深知识包装成标题党。

## 页面与交互原则

新增独立 `#/bridge` 页面，不把第一版塞进 `ProjectWorkspace.jsx`。

页面只让用户理解五个概念：我搞懂的、用户的问题、内容机会、长期议程、内容项目。Atom、Finding、Relation Graph、Chunk、Embedding 等后台概念不出现在前台。

主流程：

1. 左侧选择 Living Wiki 页面。
2. 右侧选择带来源的 Audience Problem。
3. 点击“看看怎么连接”。
4. 依次查看用户真正的问题、知识解释、认知差、核心判断、长期议程与怎么讲。
5. 可换入口、换表达方式、挑战连接、找证据缺口、看反方。
6. 用户明确点击后才保存内容机会。
7. 只有已保存机会才能建立现有内容项目。

连接较弱或没有自然连接是正式结果，不是错误。页面必须允许系统明确说“不建议硬做内容”。

## 空态与失败态

- Wiki 为空：引导去知识库整理长期知识。
- Audience Problem 为空：允许从最近洞察提取候选或手动记录。
- Preview 加载：保留已选对象，不闪空态。
- 模型失败：说明候选未生成，已保存数据未变化，可重试。
- 无自然连接：建议换知识、换问题或继续研究。
- 保存失败：候选仍保留，不能伪装成已保存。

键盘、焦点、小屏幕、disabled、错误和 reduced motion 按现役设计系统验收。页面复用现有控件与视觉语言，不另造应用壳，不用动画掩盖状态。

## 与现有页面的关系

- Wiki 增加“看看它能解决哪些用户问题”，只做临时路由 handoff，不改 Wiki 模型。
- Radar / 洞察 / 用户问题增加“看看我的知识能不能解释”，只预选 Audience Problem。
- 项目由 Opportunity 创建时，在独立 `ContentIntentPanel` 中轻量显示用户问题、核心判断、支撑知识、议程、表达动作和证据缺口。
- Today 第一轮不重做。
- `#/ideas`、`#/seeds` 与旧数据继续兼容，稳定后才退出主要导航。

临时 handoff 只存在当前前端导航状态或 URL 参数，不作为业务数据写入 localStorage。

## 迁移与兼容边界

本实验只做增量迁移：建新表、索引与约束，不读取旧 Seed/Idea 自动生成机会，不删除旧表，不改变 Series，不引入 Worker、Supabase 或 D1。迁移必须幂等，归档必须可恢复；所有写测试使用系统临时目录中的独立 `XENHO_HOME`。

Markdown 洞察报告继续是阅读产物；结构化 `audience_problem_candidates` 是机器消费层。二者互不替代。候选只有用户确认后才进入 `audience_problems`。

## 实验成功标准

1. 用户能从“我搞懂了一个东西”自然走到“它能解决谁的什么问题”。
2. 不理解后台术语也能完成连接与项目创建。
3. 系统能够诚实地说“没有自然连接”。
4. 结果先形成问题、解释、认知差和判断，而不是先吐标题。
5. 同一知识能因问题、关系或表达动作不同形成不同内容。
6. 每个已保存机会能回到 Wiki、问题来源、可选议程与证据。
7. 创建项目后继续使用现有正文、版本、发布和复盘系统。

## 明确不做

本实验不重做 Living Wiki、Today、Assistant Runtime 或整套社媒洞察；不删除 Seeds、Ideas 或兼容路由；不迁历史数据；不把 Series 改成 Agenda；不开发视觉关系图；不生成万能选题、排行榜、爆款概率或热点自动稿件；不把演示数据写入正式工作区。

## 阶段判断

本文件定义的是实验模型，不代表旧模型已经废弃。只有核心场景通过领域、API、AI、UI、重启持久化和人工验收后，才把“内容机会”提升为主要内容入口；若实验不能稳定产生真实、有来源且不过度承诺的连接，旧入口继续保留。
